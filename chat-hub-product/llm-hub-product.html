تصمیم پیشنهادی: «Compose, don't vibe-code the core»

وایت‌برد عنوان «vibe coded» دارد. برای چت UI و داشبورد این خوب است. برای حسابداری توکن، مدیریت کلید و احراز هویت خطرناک است: باگ در این‌ها یعنی پول سوخته یا کلید لو رفته.

                ┌──────────── Keycloak (OIDC on AD) ─────────────┐
                │   ← this is the "Auth API used by product too"  │
Browser (React) ─► Hub API (Python/FastAPI — our code)            │
VS Code ────────►   • SSO, RBAC, sessions                          │
                    • Accounting: org hierarchy, budgets, periods  │
                    • API key issuing (wrapper over virtual keys)   │
                    • Guardrail (local model, prompt from DB)       │
                    • Files: MinIO + parsing                        │
                    └─► LiteLLM Proxy (engine) ─► OpenRouter / direct / vLLM
                              └─► OTel → Langfuse (trace, TTFT)
                    Postgres (state) + ClickHouse (usage/trace)

چرا Hub API خودمان جلوی LiteLLM؟

SSO، RBAC، audit و سلسله‌مراتب واحد را خودمان می‌سازیم ← لایسنس Enterprise LiteLLM لازم نیست و اگر روزی LiteLLM را عوض کردیم، فقط موتور عوض می‌شود.

چرا Keycloak به‌جای Auth API خودساخته؟

محصولات دیگر سازمان هم با OIDC استاندارد وصل می‌شوند؛ نوشتن IdP از صفر یکی از پرریسک‌ترین کارهای ممکن است.

چرا Open WebUI نه؟

فرانت React خودتان را دارید؛ fork از Open WebUI هم با مشکل لایسنس برند و هم با بودجه‌ی ناموجود روبه‌رو است.

۰۲ Feasibility Assessment

وضعیت کد امروز: ریپو فقط یک فرانت React 19 + Vite است (src/lib/api.ts، src/hooks/useConversations.ts). بک‌اند نداریم، تاریخچه در localStorage است و کلید API در bundle مرورگر (VITE_API_KEY) قرار دارد. پس هر effort پایین «بک‌اند از صفر» را فرض می‌کند، با یک تیم ۳ تا ۴ نفره (فرض).

مقیاس: S ≤ ۱ هفته · M = ۲–۳ هفته · L = ۱–۲ ماه · XL > ۲ ماه (یک نفر تمام‌وقت)

Now MVP — تا Internal Alpha / Dev Beta

  • SSO با Keycloak + لاگین اجباری — پیش‌نیاز همه‌چیز. کلید از مرورگر حذف می‌شود.
  • Hub API + LiteLLM + ۳ ارائه‌دهنده با fallback — کیفیت = پذیرش. ref: LiteLLM, OpenRouter
  • انتخاب مدل از لیست مجاز per-role — مثل Cursor. ref: Cursor model picker
  • تاریخچه‌ی چت سمت سرور — localStorage برای سازمان قابل قبول نیست.
  • آپلود فایل/تصویر در چت + MinIO — بیشتر کار کارمندان عمومی با سند است.
  • بودجه‌ی ماهانه per-user (flat) + per-team — جلوی سوختن پول در پایلوت را می‌گیرد.
  • صفحه‌ی Usage در پروفایل — اعتبار مصرف‌شده و باقی‌مانده، به تفکیک مدل و روز. هشدار ۸۰٪. ref: Cursor dashboard, OpenRouter Activity
  • API key سلف‌سرویس OpenAI-compatible — پیشوند قابل اسکن (hub-sk-)، expiry، budget per-key، rate limit، راهنمای Continue/Cline. ref: OpenRouter keys
  • Trace پایه + TTFT — هر درخواست با user، model، tokens، cost، TTFT و latency. فقط metadata.
  • Guardrail در حالت Shadow (فقط متن) — برچسب می‌زند، چیزی را مسدود نمی‌کند. داده برای فاز enforce جمع می‌شود.
  • 👍/👎 روی هر پاسخ — تنها معیار «افت کیفیت».

  • Guardrail enforce برای متن + prompt قابل‌ویرایش ادمین با نسخه‌بندی و تست — مسدود روی نتیجه‌ی A6.
  • Home stats (WAU، هزینه، top models، top واحدها).
  • Auto routing (Gemma یا Jev) — مسدود روی دیتاست ۵۰۰ پرامپت برچسب‌خورده.
  • OpenAI Files API مستقل از ارائه‌دهنده.

Later

  • Guardrail تصویر و صوت (OCR + vision guard، Whisper) — حجم تصویر/صوت حساس باید اول از trace دیده شود.
  • Auth API برای محصولات دیگر — با Keycloak در عمل رایگان است. کار اصلی onboarding محصولات است.
  • Self-hosted routing برای داده‌ی حساس (سناریو ۲).
  • Agent library، Memory، RAG روی اسناد داخلی — آیتم‌های سمت راست وایت‌برد. هیچ شواهدی هنوز نداریم.
  • کارت سازمانی / پرداخت (سمت راست وایت‌برد، ناخوانا) — باید روشن شود منظور چیست.

۰۴ MVP Scope

Hypothesis

اگر کارمندان با لاگین سازمانی به مدل‌های جهانی با کیفیت برابر دسترسی داشته باشند و سهمیه‌شان را شفاف ببینند، ≥ ۷۰٪ از ۱۰۰ کاربر پایلوت بعد از ۴ هفته هنوز هفتگی فعال‌اند و ترافیک آن‌ها به سرویس‌های AI خارجی ≥ ۳۰٪ کم می‌شود. همچنین ≥ ۷ از ۱۰ dev پایلوت کلید Hub را در IDE نگه می‌دارند.

✓ In scope

  • SSO + لاگین اجباری — بدون هویت، فرضیه قابل اندازه‌گیری نیست.
  • چت با ۳ ارائه‌دهنده + انتخاب مدل — بخش «کیفیت برابر» فرضیه.
  • تاریخچه‌ی سرور + آپلود فایل — بدون این‌ها کیفیت حس‌شده پایین‌تر از ChatGPT است.
  • بودجه‌ی flat per-user + صفحه‌ی Usage — بخش «سهمیه‌ی شفاف» فرضیه + محافظ مالی پایلوت.
  • API key برای dev — بخش dev فرضیه.
  • Trace metadata + TTFT + 👍/👎 — ابزار اندازه‌گیری خود فرضیه.
  • Guardrail shadow (متن) — هزینه‌اش کم است و داده‌ای جمع می‌کند که بعداً با هیچ قیمتی نمی‌شود خرید.

✕ Explicitly cut

  • سلسله‌مراتب واحد سازمانی — ۱۰۰ نفر پایلوت را با team flat مدیریت می‌کنیم. فرضیه به آن وابسته نیست.
  • داشبورد ادمین کامل — در پایلوت، ادمین UI داخلی LiteLLM یا اسکریپت کافی است.
  • Guardrail enforce و چندرسانه‌ای — enforce روی پایلوت فقط با false positive فرضیه‌ی کیفیت را آلوده می‌کند.
  • Files API برای dev — dev‌های پایلوت با chat completions کار می‌کنند.
  • Auth API برای محصولات دیگر، Agents، Memory، Auto routing — هیچ‌کدام برای جواب دادن به فرضیه لازم نیستند.

What "done" looks like

  • ۱۰۰ کاربر از ۳ واحد + ۱۰ dev، ۴ هفته.
  • داشبورد (حتی یک کوئری SQL) که WAU هفتگی، نرخ 👍، p95 TTFT و مصرف per-user را نشان دهد.
  • مقایسه‌ی ترافیک پروکسی همان ۱۰۰ نفر، قبل و بعد.
Go: WAU ≥ ۷۰٪ و 👍 ≥ ۸۵٪ ← GA.
Pivot: اگر 👍 پایین است، مشکل کیفیت یا مدل است، نه فیچر.

۰۶ Corner Cases

C1Overspend همزمانOpen

Accounting / بودجه
سناریو: کاربر با $0.10 بودجه‌ی باقی‌مانده، ۵ درخواست streaming همزمان (مثلاً ایجنت IDE) می‌فرستد. هر کدام موقع شروع بودجه را چک می‌کند و همه رد می‌شوند.
اثر: هزینه‌ی واقعی چند برابر بودجه می‌شود، چون هزینه بعد از پایان stream محاسبه می‌شود.
منبع: الگوی شناخته‌شده‌ی metering بعد از مصرف.
راه‌حل: رزرو بودجه قبل از درخواست (بر اساس max_tokens تخمینی) + تسویه بعد از پایان + سقف concurrency per-key.

C2Stream قطع‌شدهOpen

Accounting / بودجه
سناریو: کاربر وسط پاسخ تب را می‌بندد یا Stop می‌زند.
اثر: ارائه‌دهنده توکن تولیدشده را حساب می‌کند ولی usage chunk آخر هرگز نمی‌رسد. اختلاف بین حساب ما و صورتحساب ارائه‌دهنده.
منبع: رفتار SSE. فرانت فعلی src/lib/api.ts abort دارد.
راه‌حل: stream_options.include_usage. در abort، توکن‌ها را از متن دریافت‌شده تخمین بزنید. reconcile ماهانه با صورتحساب.

C3جابه‌جایی کاربر بین واحدها وسط دورهOpen

Accounting / بودجه

اثر: هزینه‌ی نیمه‌ی اول ماه به حساب B می‌رود یا بودجه‌اش reset می‌شود.
منبع: مدل داده‌ی سلسله‌مراتبی.
راه‌حل: هزینه را در لحظه‌ی تراکنش با org_unit_id ثبت کنید، نه با join روی وضعیت فعلی کاربر.
