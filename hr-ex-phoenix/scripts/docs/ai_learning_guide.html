Part One
Concepts
A shared vocabulary: the words you see in every news item, paper and model page.

Basic concepts

From machine learning to large language models

ConceptWhat it means
Machine learning (ML)Instead of writing rules, we give the computer examples so it finds the pattern by itself.
Deep learning (Deep Learning)A kind of machine learning that uses a multi-layer "neural network". Almost all of today's models are of this kind.
Large language model (LLM)A network trained on a huge amount of text that does just one thing: predict the next piece of text. All its abilities (answering, summarizing, writing code) come from that one task.
Transformer (Transformer)The architecture (the blueprint) of almost every language model today. Its core idea is "attention".
Attention (Attention)To understand each word, the model looks at all the previous words and weighs which ones matter most. Its cost grows with the length of the text.
Multimodal (Multimodal)A model that, besides text, also takes in or produces images, audio or video.

Tokens, context window and embeddings

ConceptWhat it means
Token (Token)A piece of text the model works with; sometimes a whole word, sometimes part of a word. Pricing and speed are always measured in tokens. Persian text usually uses more tokens than the same text in English, so it is more expensive and slower.
Tokenizer (Tokenizer)The program that splits text into tokens. Every model has its own tokenizer. A good tokenizer for Persian means lower cost.
Context window (Context window)The maximum amount of text (input + output) the model sees at once; for example 128K means about 128 thousand tokens. Anything outside the window does not exist for the model.
Embedding (Embedding)Turning text into a list of numbers, so that texts with similar meaning get nearby numbers. It is the basis of semantic search and knowledge bases.
Temperature (Temperature)How random the answer is. Low temperature means a more predictable answer; for precise tasks like data extraction, set the temperature low.
Hallucination (Hallucination)When the model confidently says something that isn't true. No model is free of it; you have to control it through product design.

How a model is built

Building a chat model usually takes three stages:

  1. Pre-training (Pre-training) — the model learns to predict the next word on a huge amount of text. The output of this stage is a "base model" (Base): it knows the language but doesn't answer questions in an orderly way.
  2. Instruction tuning (SFT / Instruction tuning) — with thousands of "question → good answer" examples it learns to behave like an assistant. Output: an Instruct or Chat model.
  3. Preference alignment (RLHF, DPO) — the model is shown two answers and told which one is better. It learns to give more helpful and safer answers.

Reasoning models (Reasoning models) have one more stage: with reinforcement learning (RL) on problems whose answers can be checked (math, code), they learn to "think" before answering. That thinking uses tokens; so they are more accurate but slower and more expensive. For voice conversation, where latency matters, a non-reasoning model or a short thinking mode is usually better.

Adapting a model to our own task

MethodWhenCost
Writing a good prompt (Prompting)Always start here. With a few examples in the prompt (Few-shot) many tasks get solved.Almost zero
Retrieval + generation (RAG)When the model must answer from the organization's own knowledge (regulations, documentation). The relevant text is found and given to the model next to the question. Phoenix's knowledge base is exactly this.Low to medium
Fine-tuning (Fine-tuning)When you want a fixed behavior or output format, or a small model has to do one specific task well. LoRA is a cheap method that changes only a small part of the weights.Medium (data + hardware)
Agent (Agent) and tool use (Tool use)When the model has to do something (log a request, send an SMS, query a database). The model decides which tool to call with what input. MCP is a standard protocol for connecting tools to a model.Medium; hard to test

Running a model (inference)

Inference (Inference) means using a trained model to produce answers. These concepts matter when choosing servers and estimating cost:

ConceptWhat it means
Parameters (Parameters)The numbers inside the model that were set during training. 8B means 8 billion. More parameters usually means more capable but heavier.
Quantization (Quantization)Storing each number with fewer bits (for example 4 bits instead of 16). The model gets smaller and faster and loses a little accuracy. Rule of thumb for memory: parameters × bits ÷ 8; an 8B model is about 16 GB at 16 bits and about 5 GB at 4 bits.
Mixture of experts (MoE)The model is built from several "experts" and only a few are active for each token. For example 30B-A3B means 30 billion parameters in total, 3 billion of them active: you need memory for 30B, but the speed is close to a 3B model.
KV cache (KV cache)The model keeps the computations for earlier text so it doesn't recompute them. Long text = more memory on the GPU.
Latency and throughput (Latency / Throughput)Latency: how long one user waits. Throughput: how many people the server answers per second. You often trade one for the other. For phone calls, latency matters more.
Batching (Batching)Processing several users' requests at the same time on one GPU. Engines like vLLM do this automatically.

Inside the model card and the page's sidebar, check these:

Downloads / LikesA sign of popularity, not quality. It shows last month's downloads.

FilesThe safetensors format is safe. Old .bin or .pkl files can execute code; don't download them from an unknown repository.
Inference ProvidersWhether you can try it through providers without installing anything.

The dataset card

  • Splits — the parts of the data: train for training, validation for tuning, test only for the final measurement. A number reported on test is more trustworthy.
  • Size — number of rows or hours of audio. For audio: how many speakers, which accents, telephone or a good microphone?
  • Source and license — where the data came from and whether commercial use is allowed.

How to tell whether a repository is trustworthy

  1. The maker is a well-known organization, or the card is complete and honest (it states the limitations too).
  2. The evaluation results are reproducible: the dataset name, settings and evaluation code are given.
  3. The license is clear and fits our use.
  4. The files are safetensors and their size matches the claimed parameter count.
  5. No serious issue has been left unanswered in the Community tab.

1. Writing a good prompt (Prompting)

The system prompt (System prompt) is the text that sets the assistant's behavior: role, tone, rules, tools. Simple rules:

  • Be clear and specific. "Be polite" is not enough. "Always address the caller formally and keep every answer to two sentences at most" is better.
  • Give examples (Few-shot). Two or three "input → good output" samples work better than ten lines of explanation.
  • Write few "don'ts". Instead of "don't mention competitors' names", write "only talk about our products".
  • Break big tasks into pieces. One prompt for one task. Several tasks = several steps.
  • Version your prompts like code, and measure every change with an evaluation.

For voice: ask for short answers. Lists, asterisks and tables can't be read out on the phone.

Read: Anthropic prompt engineering docs · OpenAI prompting guide · promptingguide.ai

2. Knowledge base and RAG

RAG means that before answering, we find the relevant text in the knowledge base and give it to the model next to the question. Its stages:

StageWhat it meansCommon mistake
Chunking (Chunking)We split the document into small pieces (for example 200 to 500 tokens).A chunk cut in the middle of a sentence or a table.
Embedding (Embedding)Each chunk is turned into numbers with an embedding model and stored in a vector database.A model that doesn't understand Persian well.
Retrieval (Retrieval)The question is embedded too, and the nearest chunks are found. Combining semantic search with keyword search (BM25) is called hybrid search (Hybrid).Semantic only; it misses product names and codes.
Reranking (Reranker)A small model re-sorts the top 20 chunks more precisely and keeps the best 3 to 5.Skipping this stage; it often gives the biggest jump in quality.
Answer generationThe chunks go into the prompt and the model answers only from them, citing the source.Letting the model "guess" when the answer isn't in the chunks.
Common mistake: when RAG answers badly, the language model is often not to blame; retrieval didn't find the right chunk. First measure "was the right chunk in the top 5 results?", then look at the model.

Read: Anthropic "Contextual Retrieval" · Hugging Face Advanced RAG cookbook · LlamaIndex / LangChain RAG docs

3. Tools, agents and MCP

  • Tool calling (Tool / Function calling): you give the model the list of tools with descriptions and inputs. Instead of text, the model returns a "tool call request" with JSON inputs. Your software runs the tool and returns the result to the model.
  • Agent (Agent): a model that calls tools several times in a loop until the job is done. The more steps, the higher the chance of error (90% per step means only about 35% correct after 10 steps).
  • MCP (Model Context Protocol): an open standard for connecting tools and data to any model; you write the tool once and it works everywhere.
  • Multi-agent (Multi-agent): several models with separate roles. Powerful but expensive and hard to debug; start with one simple agent first.

Safety rules for tools: dangerous tools (payment, deletion) should require human approval; always validate tool inputs; don't force the model to guess, let it ask.

Read: Anthropic "Building effective agents" · modelcontextprotocol.io · BFCL / τ-bench papers

4. Structured output

When your software needs JSON, "please return JSON" isn't enough. Reliable methods: JSON / schema mode (Structured outputs, JSON schema) in the API, or constrained decoding (Constrained decoding) in servers like vLLM, which forces the model to produce only allowed tokens. Even then, always validate the output in code.

5. Evaluation (Eval)

Evaluation is to models what unit tests are to code. You build a set of real examples with a clear "good answer" and re-run it after every change (model, prompt, RAG).

MethodWhen
Exact metricThe answer has one definite value: classification, extraction, WER, correct tool use.
Model as judge (LLM-as-judge)The answer is open-ended (tone, helpfulness). A strong model scores it against a list of criteria. The judge is biased (it likes long answers); score 20 samples yourself too and compare with the judge.
Human evaluationFor important decisions and to validate the judge. Expensive but the most trustworthy.
Testing on real callsCalls recorded with permission, replayed on the new version. The best signal for a voice product.

Read: Hamel Husain "Your AI product needs evals" · Eugene Yan "Task-specific LLM evals" · Hugging Face LLM course

6. Fine-tuning in practice

  • First try a good prompt + RAG. Only if that isn't enough, move on to fine-tuning.
  • High-quality data matters more than lots of data. 500 to 5,000 clean examples are usually enough.
  • Tools: Hugging Face TRL, PEFT, Unsloth, Axolotl, LLaMA-Factory.
  • Distillation (Distillation): we use a big model's answers to train a small model so it becomes cheaper. Check the big model's license.
  • Always evaluate again after fine-tuning; the model may forget other things.

ToolUse

To estimate memory: weights (parameters × bits ÷ 8) + KV cache + about 20% overhead. For phone calls, measure TTFT first and then throughput.

8. Safety and privacy

Data leaksThe assistant tells customer B about customer A's information. Control access in code, not in the prompt.

Read: OWASP Top 10 for LLM Applications · NIST AI RMF

9. Cost and latency

  • API prices are per million tokens, and input and output are priced separately; output is several times more expensive.
  • Prompt caching (Prompt caching): the fixed part of the prompt (for example the system prompt) is billed cheaper and processed faster.
  • A small model for simple tasks: routing between a small and a big model (Routing) can cut cost several times over.
  • Streaming (Streaming): feed the answer to TTS piece by piece; don't wait for the answer to finish.
  • Total latency = end of turn + ASR + TTFT + TTFA + network. Measure each one separately.

10. Model licenses

LicenseWhat it means
Apache 2.0, MITPermissive; commercial use and modification are allowed. The best case.

Reminder: the model's license, the training data's license and the license of upstream models (for example distillation from a closed model) are three separate things. Before commercial use, always read the LICENSE page.

11. Multimodal

  • Vision-language model (VLM): understands photos or document scans; for example reading forms and invoices.
  • Audio-language model (Audio LLM): instead of a separate ASR, it hears the audio directly and also picks up tone and emotion.
  • Speech-to-speech (Speech-to-speech, Realtime): one model for listening, thinking and speaking; very low latency, but less control over each step and weaker Persian.
  • A separate chain (ASR → LLM → TTS) is still more controllable and more measurable for Phoenix; but the trend is toward integrated models, so keep following it.

Benchmarks and metrics

A benchmark (Benchmark) is a standard test: a set of questions with correct answers. A metric (Metric) is the number that comes out of the test (for example percent correct). A leaderboard (Leaderboard) shows the results of several models on one or more tests.

The most important language-model benchmarks

NameWhat it measuresWatch out
MMLU, MMLU-ProGeneral knowledge in 57 subjects, multiple choice with four options (Pro: ten options and harder)MMLU is almost saturated; all big models score high.
GPQA DiamondPhD-level science questions that are hard to answer even with searchOnly 198 questions; a gap of a few percent may be random.
HLEHumanity's Last Exam: very hard questions from expertsFor comparing frontier models; not very relevant for day-to-day work.
AIME, MATHCompetition mathA sign of reasoning ability, not conversational ability.
LiveCodeBench, SWE-benchWriting code; SWE-bench fixes real issues in GitHub repositoriesDon't compare the Verified and Pro versions with each other.
IFEvalFollowing instructions exactly ("in 3 sentences", "without commas")Important for our product: the assistant must respect the format.
BFCL, τ-benchCalling tools correctly; τ-bench is a multi-turn conversation with a simulated user and business rulesThe benchmark closest to the Phoenix assistant (asking questions, tools, following policy).
RULER, NeedleActually using long contextA 1-million-token window doesn't necessarily mean all of it is used well.
MTEBEmbedding quality for search, classification and clusteringFor the knowledge base. It has a Persian version too (see below).
LMArenaUser votes between two anonymous answers; an Elo scoreIt measures user taste; long, well-formatted answers get more votes. Turn on "style control".

Why one number isn't enough

ProblemWhat it means
Contamination (Contamination)The test questions were in the training data; the model memorized the answer instead of understanding it. "Live" benchmarks that keep adding new questions (like LiveCodeBench) reduce this problem.
Saturation (Saturation)All models are near 90% or higher; it no longer shows any difference.
Different setupsOne model with 5 examples and thinking, another with no examples. The numbers aren't comparable. Look for 0-shot, CoT, thinking, pass@1 in the table.
Confidence intervalIn the arena, each score has a "±" next to it. If two models' intervals overlap, they are effectively tied.
Self-reported by the makerThe number on the model card was measured by the maker itself. An independent number (Artificial Analysis, Epoch AI, the arena) is more trustworthy.
LanguageAlmost all benchmarks are in English. A high score in English does not guarantee good Persian.
Golden rule: leaderboards only build a shortlist. The final decision comes from testing on our own data: 50 to 200 real Persian samples from Phoenix's work, with a clear metric.

Special chapter: voice

Phoenix is a voice pipeline: speech detection → speech-to-text → language model → text-to-speech, plus end-of-turn detection. The foundations of this pipeline are covered in the "Technical Dossier" (TECHNICAL_DOSSIER, the audio fundamentals section). Here we only learn the numbers.

Speech-to-text (ASR / STT)

WER = (deleted words + inserted words + substituted words) ÷ the number of words in the reference text. Example: the reference text is "می‌خواهم مرخصی بگیرم" ("I want to take leave", 3 words), and the model wrote "میخوام مرخصی بگیرم" (the colloquial form). If "میخوام" is counted as wrong, WER = 1 ÷ 3 ≈ 33%.

Why you should also look at CER for Persian: in Persian, the zero-width non-joiner ("می‌خواهم" vs "میخواهم"), the Arabic forms of "ی" and "ک", and colloquial spelling ("میخوام") push WER up for no good reason, even though the meaning is correct. CER is less sensitive. More important: before computing, apply the same normalization (Normalization) to both texts — one form for "ی" and "ک", the ZWNJ, numbers and punctuation. Reputable leaderboards state their normalization method.
MetricMeansFor Phoenix
WER / CERError rate (lower is better)Measure on 8 kHz telephone audio, not studio audio. The difference can be several-fold.
RTFxHow many times faster than real time. RTFx = 100 means one minute of audio in 0.6 secondsImportant for call analytics (CCA), which runs in batches.
Streaming latencyIn live mode (Streaming), how soon after something is said the text arrivesFor the voice agent (IVA) it matters even more than WER.
Short-form / Long-formShort audio (a few seconds) or long audio (a whole call)Call analytics = long; live conversation = short.
Diarization (DER)Separating "who spoke when"; DER is its error rateNeeded for single-channel calls.

Text-to-speech (TTS)

MetricMeans
MOSListeners give a score from 1 to 5. Above 4 means natural. It is expensive and slow.
CMOSComparing two voices side by side: which is better and by how much. More sensitive than MOS.
UTMOS and similarA model that estimates MOS automatically. Good for quick comparisons, but less tested on Persian.
Reverse WER (intelligibility)The generated audio is turned back into text with ASR; if WER is low, the voice is clear. It catches mispronounced numbers and names.
SIMHow similar the voice is to the reference speaker (in voice cloning).
TTFATime to the first chunk of audio. For phone calls, under a few hundred milliseconds is a good target.
Arena EloListener votes between two voices (TTS Arena, Artificial Analysis Speech Arena).

Speech and turn detection (VAD, Turn detection)

MetricMeans
End-of-turn latencyFrom the moment the user goes quiet to the moment the system realizes it's its turn. Low = fast, but…
Premature cut-off (False endpoint)…the system may cut the user off in the middle of a pause ("خب… راستش…", "well… actually…"). These two trade off against each other.
False interruption (False barge-in)An "اوهوم" ("uh-huh") or background noise makes the assistant stop talking.
Total response latency (Voice-to-voice latency)From the end of the user's speech to hearing the assistant's first sound. The sum: end of turn + ASR + the language model's TTFT + TTFA. The most important user-experience number on the phone.
How this relates to Phoenix: the latest change in the repository (commit 537415cb8) improved end-of-turn detection in AIVA by asking the language model ("is the sentence complete?"). This is exactly the trade-off between "end-of-turn latency" and "premature cut-off"; to measure it, report both numbers together.

Part Three
Models
Well-known model families, what each one is good at, and which to try first for Phoenix.

Well-known models and what they are for

Before you read: this list is organized by family, not exact version. A new version comes out every few weeks. This chapter reflects the state as of October 2026, and part of it comes from secondary sources (blogs and aggregators). Before any decision, read the official model card and license on Hugging Face. The "recent versions" column is only there so you know what name to look for.

How to read a model's name

Example: Qwen3-30B-A3B-Instruct-2507-FP8 means the Qwen family, generation 3, 30 billion parameters in total with 3 billion active (MoE), the chat version (Instruct), built in July 2025, at 8-bit precision. The abbreviations are in the Abbreviations glossary chapter.

1. Open language models (Open-weight LLM)

"Open" means you download the weights and run them on your own server. This matters for privacy and cost.

FamilyMakerSizes and licenseMain use and strengthWatch out
Qwen
(Qwen3, 3.5, 3.6)		 Alibaba From under 1B to hundreds of B; both dense and MoE (for example 30B-A3B, 35B-A3B). Most versions are Apache 2.0. All-rounder and multilingual. Conversation, code, math, reasoning, tool calling. It has a big family: text, vision (Qwen-VL), code (Qwen-Coder), embedding, ASR and TTS models. The first candidate for a Persian assistant. Measure Persian quality on your own data. The heavier versions think and get slower.
Gemma
(Gemma 3, 3n, 4)		 Google From about 1B to about 30B; "E" versions for small devices. Generation 4 is reported to be Apache 2.0 (older generations had a custom license). Small and efficient models. Good multilingual support (100+ languages), multimodal (images, and in some versions audio), long context window. Suitable for a single ordinary GPU and edge devices. Read each generation's license separately. Usually behind Qwen on tools and code.
Llama
(Llama 3.x, 4)		 Meta 1B to hundreds of B; Llama 4 is MoE. Custom license: Llama Community License. Big ecosystem. The most tools, tutorials and fine-tuned versions in the community. A good base for fine-tuning. Llama Guard for safety. The license has conditions (user cap, attribution). Persian is not officially supported; you have to test it.
DeepSeek
(V3, R1, V4)		 DeepSeek Very large (hundreds of B, MoE). Most versions are MIT. There are smaller "Distill" versions too. Reasoning and code at low cost. R1 was the well-known open reasoning model. For hard analysis, math and programming. Distills on Qwen/Llama for small hardware. Running the full model needs a multi-GPU cluster. On the phone, long thinking = latency.
Mistral
(Small, Medium, Large, Mixtral, Ministral)		 Mistral AI Small to large; some Apache 2.0, some with a research license or API-only. A European model, fast and efficient. European languages, tool calling, code (Codestral, Devstral), audio (Voxtral). Average Persian. Each model's license is different.
gpt-oss OpenAI Two sizes, about 20B and 120B (MoE), Apache 2.0. Reasoning and tools; adjustable thinking level (low/medium/high). Text only. English-centric; weaker Persian.
GLM
(GLM-4.x, 5)		 Zhipu / Z.ai Medium to large (MoE), usually with a permissive license. Code and agents (multi-step work with tools). High on the code and agent leaderboards. Mostly Chinese-English.
Kimi
(K2, K3)		 Moonshot AI Very large (over a trillion, MoE); a modified MIT license. Agents and code, long context. Close to the leading closed models on some tests. Very heavy hardware; in practice used through an API or a hosting service.
MiniMax MiniMax Large, MoE; permissive license in recent versions. Agents and code, very long context. Heavy.
Phi Microsoft Small (a few B), MIT. A very small model that is good at math/reasoning. For weak devices and experiments. Limited general knowledge and multilingual ability.
OLMo, SmolLM, Granite AI2, Hugging Face, IBM Small to medium; Apache 2.0. Fully open (training data and code are published too). OLMo for research and transparency; SmolLM for small devices; Granite for enterprises. Usually weaker than Qwen/Llama.
Persian models
(for example Dorna, PersianMind, Sialk…)		 The Iranian community and companies Usually fine-tuned on Llama/Qwen/Gemma; the license is inherited from the base. Improved Persian on top of base models. Check the Open Persian LLM Leaderboard. Uneven quality; they often fall behind the newer general base model. Always test them.

Assessing a new model in 10 minutes

  1. Who built it and under what license? If it isn't commercial, stop right here.
  2. Size and memory: with the "parameters × bits ÷ 8" rule — does it fit on our server?
  3. Persian: is it in the card? Is it on the Persian leaderboard?
  4. Independent numbers: where does it rank on Artificial Analysis or the arena? Not just the maker's card.
  5. Manual test: 5 real sentences from Phoenix's work (an HR question, a colloquial sentence, a number and a date) in the demo.
  6. Speed: TTFT and tok/s (or for audio: RTFx and streaming latency).
  7. Verdict: "worth / not worth a full test" and one reason.

Running it yourself

ToolWhen
SpacesThe fastest way; nothing to install.

transformers (Python)Full control; for evaluation on our own data. For audio: pipeline("automatic-speech-recognition")

The "don't trust a single number" checklist:
  • Is the test setup (number of examples, with or without thinking) the same?
  • Is a confidence interval or the number of questions given?
  • Who measured it?
  • Is the benchmark saturated or contaminated?
  • Is it relevant to our language and type of data (Persian, telephone, colloquial)?

Exercises

  1. Read three model cards. Find a language model, a speech-to-text model and an embedding model that support Persian. For each one, fill in this table: maker · license · parameters (total/active) · precision and format · context window · Persian? · independent number · memory needed · verdict.
  2. Read a leaderboard. On LMArena, find two models that are close to each other. Do their confidence intervals overlap? Do they swap places with "style control"?
  3. WER on our own audio. Prepare 20 clips of Persian telephone audio (with permission and without personal information) with their reference transcripts. Run two speech-to-text models, normalize the texts and compute WER and CER with the jiwer or evaluate library. Compare the number with the Persian leaderboard: how different is it, and why?
  4. Total latency. In a Phoenix test call, write down four times separately: end of turn, ASR, the language model's TTFT, TTFA. Which one contributes the most?
  5. One-page report. Assess a new model with the "10-minute" checklist and write up the result for the team.
