Call path: from dialing to the IVA (Intelligent Virtual Assistant) Agent — where the Pipeline starts

Everything in Phoenix starts with a phone call; but the Code in this repository only takes responsibility from the moment the call has entered a LiveKit Room as a Participant. Before that there is a long chain of operator layers, Backbone, data center, SBC (Session Border Controller) and SIP (Session Initiation Protocol); if any one of them is not ready, even the best LLM (Large Language Model) will not get a single word to the caller. This chapter opens up the whole chain layer by layer — from the "service number" to the first greeting sentence —, draws the "outside the repository / inside the repository" boundary precisely, and for each layer gives a "done" criterion, tests, failure symptoms and questions to ask in meetings.

New label TELECOM: standard telecom/VoIP knowledge (SIP (Session Initiation Protocol) behavior, RTP (Real-time Transport Protocol), SBC (Session Border Controller), Codec, common figures). These are not visible in this repository, and MCI's actual network topology (Zone, Backbone, SBC, fiber path) is not assumed in this document — only the common industry pattern. Confirm any figure that carries this label with the Core/Network/VoIP team before committing to it. Claims about Phoenix are still documented with CODE.

3. SIP (Session Initiation Protocol) vs RTP (Real-time Transport Protocol) — Signaling and Media

The most important distinction to know in Voice meetings: SIP (Session Initiation Protocol) does not carry the conversation audio. SIP says how a call is set up, changed and ended (Signaling); the actual audio travels with RTP (Real-time Transport Protocol) over UDP (User Datagram Protocol) (Media). The Media parameters (IP (Internet Protocol), port, Codec) are negotiated inside the SDP (Session Description Protocol) body of the SIP messages — which is why a misconfigured Firewall/NAT usually causes "the call connected but there is no audio", not "the call did not connect".

3.1 Networking — UDP (User Datagram Protocol), TCP (Transmission Control Protocol), TLS (Transport Layer Security) and the differences

Every connection in Phoenix rides on several layers: IP sets the address and the route; TCP or UDP sets how packets are delivered; TLS or DTLS (optional) adds encryption and authentication; and on top sits the application protocol (SIP, RTP, HTTP, gRPC, Kafka). Most "the call connected but …" failures are explained by which layer has the problem, not by the application Code.

2. Why audio runs over UDP, not TCP

In a live conversation, a packet that arrives 200ms late is no longer useful. In TCP, a lost packet holds up all the packets after it too until it is retransmitted (Head-of-Line Blocking), so the audio cuts out for a second and then arrives compressed. In UDP, the same lost packet only causes a short "dropout" (20ms) in the audio and the conversation goes on. That is why in RTP we accept loss and smooth out arrival-time variation with a Jitter Buffer.

CriterionUDPTCP

Crossing Firewall/NATHarder: there is no "connection", so a port range must be opened explicitlyEasier: the Firewall tracks connection state

Bandwidth of one G.711 call: one packet every 20ms → 50 packets per second; Payload 160 bytes + Header (RTP 12 + UDP 8 + IP 20 = 40) = 200 bytes → 80 kbps at the IP layer; with the Ethernet Header (18 bytes) ≈ 87 kbps in each direction — the same figure used for capacity sizing in checklist step 5. Because the packets are small and numerous, packets per second matters more to the Firewall and Router than byte volume.

3. SIP: choosing a Transport — UDP, TCP or TLS

Transport Port Advantage Drawback / trap
UDP 5060 Simple and light; the default for most operators; SIP does its own Retransmit A large message (an INVITE with many Headers and a large SDP) exceeds the MTU (~1500 bytes) and gets Fragmented or lost; per RFC 3261, a message larger than about 1300 bytes must go over TCP. Keep-Alive is needed to keep the NAT binding open.
TCP 5060 Large messages without Fragmentation; persistent connection; Firewall-friendly A dropped connection has to be re-established; Head-of-Line blocking between calls sharing a connection; the cost of keeping connections open for thousands of Trunks
TLS 5061 Signaling is encrypted; the peer's identity is verified with a Certificate Certificate expiry is the most classic cause of a sudden Trunk outage; the CA and name (CN/SAN) must match on both sides; the initial Handshake is slower. TLS encrypts only Signaling; the audio (RTP) is not encrypted unless SRTP is enabled too.

5. NAT (Network Address Translation) — why it is audio's number-one enemy

NAT translates a private address inside the network (e.g. 10.x.x.x) into a public/other address on the way out, and for the return path keeps a table of "who opened which connection". Common types: SNAT (rewriting the source address for outbound traffic), DNAT (rewriting the destination address for inbound traffic, as in Port Forward) and PAT (several devices sharing one public IP with different ports). It is harmless for web and APIs; for VoIP it causes problems because:

  1. SIP carries addresses inside the message text. The media IP and port are written in the SDP body (the c= and m= lines) and in the Via and Contact headers. NAT only rewrites the IP packet header, not the SIP text; so the other side sends audio to a private address that is unreachable from outside → "the call connected but there is no audio" or "audio is one-way".
  2. RTP runs over UDP and has no "connection". NAT opens a temporary "hole" for each stream and closes it if no packet passes for a while (usually 30s to a few minutes). A long user silence or a Hold can cut the audio.
  3. The media port is dynamic. Every call gets a fresh RTP port (negotiated in the SDP), so you cannot write a fixed DNAT rule for it.

6. Firewall and ACL (Access Control List): what must be open

A firewall allows or rejects packets based on source, destination, port and protocol. Two kinds: Stateless (each packet is checked separately; both directions must be opened explicitly) and Stateful (it tracks the connection and automatically allows return packets). For TCP the connection state is clear; for UDP the firewall only creates a "temporary flow" with a timeout. An ACL (Access Control List) is a simple Allow/Deny list on routers and switches.

  • Testing properly: Ping (ICMP) and an open TCP port tell you nothing about UDP. You must send a real OPTIONS message and use packet capture (e.g. tcpdump or sngrep) to see that the INVITE arrives, which address the SDP carries, and that RTP passes in both directions (checklist step 9).

9. RAG (Retrieval-Augmented Generation) or fine-tuning: where each fits in Phoenix

Section 11 says what is in the repository; this chapter says why it is there, when to use it, when not to, and which capabilities of these same tools are still unused and could become product features. The goal is that any project member can make decisions about tool choice, cost and roadmap without reading the code.

Label rule in this chapter: the "In Phoenix" row comes from the code (CODE). General principle: polyglot out of necessity, not taste

Databases and storage

A simple rule: each kind of data has its own place. Transactions and relations → PostgreSQL; analysis over millions of rows → ClickHouse; semantic search → Qdrant; temporary, fast data → Redis; files (audio, backups) → MinIO.

PostgreSQL: the transactional source of truth

What it is A relational database with ACID, rich indexing, JSONB and extensions.
Selection philosophy The safe default: any data that must be correct, unique and joinable (users, roles, calls, tags, trends, annotations) goes here. Django and GORM both support it natively.
In Phoenix The shared schema of coa-api and grogu (the tables calls, call_records, call_ai_tags); aiva, adcs, aqa. The Celery broker of coa-api is Postgres itself (sqla+postgresql). HA with Stolon, postgres-exporter for metrics, archive_old_calls with pg_dump to MinIO, and an experimental pg-scaler operator.
What else we could do INFERENCE Partitioning of the calls table by month instead of manual deletion, so archiving means detaching a partition; Row-Level Security to separate HR data from customer data in one database (multi-tenant); pgvector for small collections instead of a separate service; Logical replication / CDC (Debezium) to send changes to Kafka with no extra code; LISTEN/NOTIFY for lightweight events; Full-text search over ticket text.
When not / risk Heavy aggregation over millions of calls (that is ClickHouse's job); Postgres as a Celery broker creates a lot of polling at high scale. Sharing one schema between two services (coa-api and grogu) means every migration must be coordinated.

What it is A distributed, durable log; a message is not deleted after it is read, so several independent consumer groups and replay are possible.

Audio files: mono, stereo, multitrack and codecs: which for what?

A channel is an independent audio "stream" inside a file. Mono has one channel and all voices are mixed in it. Stereo has two channels (left and right). In music the two channels give a sense of space; in a contact center the common method is split-stereo (or dual-channel): each speaker on one channel, caller left, agent right. Multitrack means each speaker is recorded in a separate file; LiveKit Egress does exactly this.

Type Advantage Drawback Suited for
Mono Smallest size; the default input of most ASR and VAD models The two voices are mixed; speaker separation (diarization) needs a model and makes errors; overlapping speech cannot be separated Live streaming to ASR/VAD during the call (rust/vad only accepts 16 kHz mono); single-speaker voice messages
Split-stereo Speaker separation for free and error-free; detection of overlap and interruptions; talk-time ratio; each side's silence; a single file that is simple to play and store Twice the size of mono; the two tracks must be time-aligned Post-call analysis (CCA): the overlap, satisfaction and greeting tags depend exactly on this separation; the input of voice-segmenter
Multitrack Highest quality and flexibility; each track with its own codec and sample rate; also works for more than two people (conference, supervisor) Several files; tracks do not necessarily start at the same time and alignment needs timestamps Initial raw recording (Egress); multi-party calls; model training

The sample rate (samples per second) determines which frequencies are kept (maximum = half the sample rate):

Sample rate Where Note
8 kHz (narrowband) Traditional phone network, G.711 Frequencies above 4 kHz are removed; the letters "س، ش، ف" (s, sh, f) sound alike and ASR accuracy drops
16 kHz (wideband) Standard ASR and VAD input, HD calls (G.722, AMR-WB) The sweet spot for speech
24 to 48 kHz WebRTC/Opus, TTS output, music No benefit for speech sent to ASR; it only increases size

Codec and container: approximate size for one hour of mono audio:

Format Size/hour Characteristics Suited for
WAV / PCM 16-bit, 16 kHz ~115 MB Uncompressed and lossless; direct processing without decoding ASR/VAD input, intermediate processing
FLAC ~50–70 MB Compressed and lossless Archive for model training or legal requirements
G.711 (μ-law/A-law) ~29 MB The native phone codec, 8 kHz, 64 kbps, near-zero latency Transport over SIP/RTP
Opus (in OGG/WebM) ~7–14 MB The best speech codec at low bitrates (16–32 kbps); the native WebRTC codec Egress recording (this OGG), long-term archive, playback in the dashboard
MP3 ~7 MB at 16 kbps Plays everywhere; but for speech at low bitrates it is worse than Opus Sharing and general playback

Glossary

Term Meaning
IDOR — Insecure Direct Object Reference Insecure Direct Object Reference — a class of access-control vulnerability: the server takes an identifier (such as call_id or a file name) from the user and fetches the record directly, without checking that it really belongs to that user or falls within their access. Example in this document: with GET /api/v1/files?name=<call-id>.wav, changing the call-id lets anyone download other people's call recordings.
VAD — Voice Activity Detection Voice Activity Detection — an algorithm (usually a lightweight model) that runs in real time on the audio stream and separates frames containing speech from silence/background noise. VAD output is the input to turn detection, and in the voice agent architecture (LiveKit) it runs before ASR.
Turn Detection / Endpointing The logic that decides, from VAD output (and sometimes linguistic signals), that the user has finished their turn and it is now the agent's turn to respond. Detecting too early cuts the user off mid-sentence; detecting too late adds a noticeable delay before the agent responds. Tuning it is a direct trade-off in the conversation experience.
Barge-in The ability for the user to speak while the agent is talking (TTS) and stop the agent — natural behavior in human conversation. In this project's code it is controlled by flags such as allow_interruptions in chatbot-iva-agent/src/agents/agentlib.py and entrypoint.py (for example, interruption is disabled in special cases such as the greeting message or user silence).
Egress In LiveKit, the process of exporting/recording a room's content (real-time audio/video) to a file or external stream (e.g. saving to object storage). In this project it is used to record the user's and the agent's audio tracks (participant_track_path, agent_track_path) so they are available later for offline ASR or audit.
RAG — Retrieval-Augmented Generation Retrieval-Augmented Generation — a pattern in which, before the LLM is called, relevant documents are retrieved from a knowledge base (vector DB / knowledge base) and added to the prompt as context, so the answer is based on the organization's actual data rather than only the model's pre-trained knowledge. Its main benefits are less hallucination and the ability to update knowledge without fine-tuning.
ReAct An agent design pattern (Reason + Act) in which the model iterates between "reasoning about the next step" (Reason), "running a tool/action" (Act) and "observing the result" (Observe) until it reaches a final answer; the basis of many agentic frameworks, including the tool-calling structure in this project.
SSE — Server-Sent Events Server-Sent Events — a one-way (server to client) HTTP protocol that pushes text events one after another over an open connection; in this project it is used to stream the LLM response incrementally (token by token) to the chat client, without needing a full WebSocket.
DLQ — Dead Letter Queue Dead Letter Queue — a separate queue (on Kafka/RabbitMQ) that holds messages whose processing has failed repeatedly and that the main consumer could not complete; instead of the message being lost or retried forever, it allows later manual review/replay.
Circuit Breaker A service resilience pattern: when calls to an external dependency (such as the ASR service) fail repeatedly, the circuit breaker temporarily "opens" the call path so new requests fail immediately and don't put load on the broken service; after a time interval it tests again (Half-Open) and, if that succeeds, closes the path. It is implemented in golang/grogu/internal/circuitbreak and used in golang/grogu/internal/asr/service.go.
MCP — Model Context Protocol Model Context Protocol — an open standard for connecting language models to external tools/data sources in a uniform way (the MCP server advertises capabilities, the model/agent calls them), instead of writing each integration ad hoc. In this project agentlib-plugin-mcp plays this role.
WER — Word Error Rate Word Error Rate — the standard ASR accuracy metric: the sum of substituted, deleted and inserted words in the transcribed text divided by the total number of words in the reference text. Lower WER means a more accurate transcript; it complements the transcript_confidence metric, which this project's schema stores per utterance.
Service Number (sarshomareh) The short/special number a customer dials to reach a service. Allocating it only provides an entry identifier; the service is not usable until routing, connectivity, the SBC and the SIP trunk are ready.
Zone / Core Network (operator core network) The central part of the operator's network that controls and routes calls; it decides which trunk/destination a call to a service number goes to.
Signaling Control messages for setting up, changing and ending a call (who, to where, available or not, connected or dropped). Separate from the audio itself (media).
Backbone The operator's main high-capacity transport network (fiber + core equipment) that connects zones and data centers. "Connecting to the backbone" means connectivity + routing + IP + security, not just a cable.
VLAN / ACL / QoS — Virtual Local Area Network / Access Control List / Quality of Service VLAN: logical network separation on one physical infrastructure. ACL: allow/deny list for traffic by IP/port. QoS: prioritizing voice traffic (e.g. DSCP EF) to reduce jitter and loss.
SBC — Session Border Controller Session Border Controller — the security and control gateway for SIP calls at the network edge: session control, security, NAT traversal, topology hiding, capacity limiting and message normalization. The operator's SIP trunk usually terminates on it.
SIP — Session Initiation Protocol Session Initiation Protocol (RFC 3261) — the signaling protocol for voice calls over IP, with messages such as INVITE, 180 Ringing, 200 OK, ACK, BYE, OPTIONS and MESSAGE. It does not carry the audio itself.
SIP Trunk (Session Initiation Protocol Trunk) A logical SIP connection between two systems (e.g. the operator and the SBC) with agreed peer IPs, transport, concurrent channel limit and number format.
RTP — Real-time Transport Protocol Real-time Transport Protocol — carries the audio itself (media) over UDP, usually in 20ms packets. Its path may differ from the SIP path.
SDP — Session Description Protocol Session Description Protocol — the body of SIP messages that negotiates the media IP, port and codecs (offer in INVITE, answer in 200 OK). A wrong IP in the SDP is a common cause of "no audio".
Codec (G.711 — ITU-T standard; PCMA/PCMU) An audio encoding algorithm. G.711 (PCMA/PCMU) is the common telephony standard: 8 kHz, 64 kbps net (~87 kbps with overhead). STT in IVA works with this narrowband audio.
Jitter / Packet Loss (delay variation / lost packets) Jitter: variation in the arrival time of RTP packets; packet loss: lost packets. Both cause choppy/robotic audio and lower STT accuracy.
NAT Traversal — Network Address Translation Traversal The problem of SIP/RTP passing through NAT: the internal address written in the SDP/Via is not reachable from outside; the result is one-way audio or the call dropping after ~32 seconds. The SBC usually solves it.
LiveKit SIP / Dispatch The LiveKit bridge that turns a SIP call into a room and makes the caller a participant with identity sip_+98…; the dispatch rule decides which agent worker takes the call. SIP headers appear as sip.h.* in the participant attributes.
SIP MESSAGE (Redirect) — Session Initiation Protocol MESSAGE How Phoenix hands off to a human agent: instead of the standard REFER, sip-messager sends a MESSAGE with X-Resolution and X-Destination (default 6040) to the hop extracted from Via and expects a 202.
HA / Failover — High Availability High Availability: several nodes/data centers so that the failure of one does not stop the service. Failover: automatic transfer of traffic to a healthy node.
Concurrent Calls The number of simultaneous calls — the main unit of capacity: each concurrent call uses one SIP session, two RTP streams, one agent job and one concurrent STT/LLM/TTS session.
Fine-tuning Retraining the parameters of a pre-trained model on a specific dataset so it learns a behavior, tone or specific task better. Unlike RAG, it is not suited to changing knowledge (prices, procedures). RAG and fine-tuning can be combined: RAG supplies knowledge, fine-tuning shapes behavior. Phoenix has no fine-tuning code.
k-anonymity A statistical privacy model: data or aggregate statistics are shown only when at least k records/people are behind the group, so that combining filters cannot identify a specific person within the group (e.g. not showing "negative sentiment" for a group of only 2 people, which would effectively reveal identity). In this document it is used as the suppression mechanism for small groups (PRV-05).
