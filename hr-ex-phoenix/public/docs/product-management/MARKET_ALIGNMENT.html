MCI's needs and the market: how to build the COA, AIVA and Chatbot product

This document looks at which of MCI's needs every other customer also has, and which ones are specific to MCI. Then it proposes how to build the product so it works for both. The main focus is this question: how do we build "each manager sees only the data of their own deputy division or department"?

Audience: all project members · Version 0.2 · 7 Oct 2026 · Inputs: the EX pilot Fit-Gap sheet (87 requirements, 10 decisions, 6 Backlog items), the actual status of each requirement in the code (from verdicts.tsv and the Product Dossier), the competitor analysis in chapter 25 of the Product Dossier, the roadmap (ROADMAP_FA) and a fresh search of competitor documentation (sources in chapter 12).

Source labels: CODE from the code · FIT-GAP from the agreement sheet · DOSSIER from the Product Dossier · WEB from competitor sites (chapter 12) · INFERENCE our opinion; check before committing.

1. Summary

The main point of this document: most of MCI's needs are not specific to MCI. MCI described them in its own terms, but the big competitors all have them. For example:
  • "Deputy division → general department → department" is the same organizational hierarchy that every competitor has.
  • "Only the system administrator sees identity" means we tier access to data.
  • "Small groups are not shown" means a minimum number of people for a report to be shown.
  • "Knowledge belongs only to our department" means each part of the knowledge has one owner.
Our proposal: build these once, in a generic form. Then, for MCI, only configure them. That way the next customer, or the next phase for this same customer, needs little new code.
52generic requirements: any similar customer wants the same thing. They must be in the product itself.
22configuration requirements: the capability is generic, only its value differs per customer (like the welcome text).
14MCI-specific requirements: project work, like the trunk-number connection or SAP.

These three numbers add up to 88, not 87, because SEG-07 is both generic (connecting to an HR system) and MCI-specific (connecting to SAP itself). The full table of 87 rows is in chapter 4. FIT-GAP 87 rows · INFERENCE classification

Five key points

  1. Our main problem is "access by organizational unit", not AI. The AI analysis part and the conversation part are almost ready. But today the system does not know which deputy division or department each employee or each call belongs to. No service has that information.
    The Auth service (login and permissions) only has a flat list of permissions. Permissions are not tied to any deputy division or department.
    In COA, a user has only two modes: either they see only their own calls, or they see all calls. There is no "only my deputy division's calls" mode.
    This problem does not show up in the MVP, because it was decided that only the EX team sees all the data. But the first Backlog item ("each manager sees only their own area") needs exactly this. CODE python/adcs-auth/adcs_auth/jwtoken/serializers.py:29-37 · python/coa-api/coa/apps/main/services/call.py:849-855
  2. Competitors all use the same method. For each user they set three things:
    • Role: for example, manager or specialist.
    • Scope: which part of the organization. For example, "the technology deputy division and all departments under it".
    • Level of detail: only numbers and charts, or comment text too, or sensitive comments too.
    Qualtrics, Viva Glint, Peakon and Medallia all do this (chapter 5).
  3. Proposal: design the "access management" part right now and build its simple version. This part includes: the organization tree, setting each user's scope, data tiering, the minimum number of people and the access log.
    In the MVP this part has the simplest configuration: the EX team sees the whole organization, there is one Knowledge Base, and only the system administrator has access to identity, in necessary cases. This is exactly what the EX decisions say.
    After the pilot, to let a deputy division's manager see only their own deputy division, we only need to add one setting. No new project is needed.
  4. Shape of the product:
    • AIVA handles the phone conversation.
    • Chatbot runs the same conversation in text. Same questions, same knowledge and same settings. Only the channel differs.
    • COA analyzes all conversations and reports on them.
    • adcs-auth decides who sees what.
    Details in chapter 8.
  5. What not to build: multi-customer SaaS on one server (for now, a separate install per customer, as in the roadmap), a separate code branch for MCI, and any page that shows an employee's name or number to a manager. DOSSIER ROADMAP_FA §3-C "Real multi-tenant SaaS: not for now"

11. Risks and things we must not do

RiskWhat to do
Building too much generic work before the second customerMake only the tables and the access-check points generic. The access-management screen and the program builder come later. Rule: every block in the MVP must work with a simple configuration.
Identity leaking through AQAPut the restriction in the database itself, not in the Prompt. Until it is ready, AQA is only for people with "whole organization" access.
A high minimum group size hides too much dataDon't drop a small unit's data; count it in the parent unit. Report to EX what percentage of data was hidden so they can decide knowingly.
An employee's unit is recorded wrongly from an outdated fileRecord the employee file's date on each message. For SEG-04, document the owner and the update schedule in writing.
MCI-specific code gets into the productReject any code that hard-codes the word "deputy division" or "MCI". These belong only in configuration.
The sensitive-case queue gradually turns into a complete whistleblowing productDossier red line: legal anonymity, case management and regulatory requirements are not for now. DOSSIER §25.8 · ROADMAP_FA §3-C
