لایهٔ LLM: کلاینت OpenAI، استریم، usage و متریک‌ها

فعال

یک کلاس کلاینت LLM به نام OpenAILLM با هر سرور سازگار با OpenAI حرف می‌زند. از Responses API جدیدتر استفاده می‌کند، نه Chat Completions، و به‌طور پیش‌فرض استریم می‌کند. یک task جانبی برای هر فراخوانی استریم‌شده زمان تا اولین توکن، زمان کل و مصرف توکن را اندازه می‌گیرد.

پارسر استریم

OpenAILLMParser رویدادهای Responses API را به chunk تبدیل می‌کند: deltaهای متن ← LLMToken، deltaهای reasoning ← LLMReasoningToken، یک فراخوانی تابع کامل‌شده ← FunctionCall و در response.completed مصرف توکن ← LLMUsage (agentlib/llm/openai/parser.py:98-203).

گزارش usage و متریک‌ها

  • برای هر فراخوانی استریم‌شده، یک task مانیتور مقدار TTFT و مدت را در llm_ttft_seconds{usecase} و llm_response_latency_seconds{usecase,stream} ثبت می‌کند و یک رکورد LLMMetrics با توکن‌های ورودی، cached، خروجی، reasoning و کل می‌سازد (agentlib/core/abc/chat/llm_stream.py:57-103).
  • هر فراخوانی llm_generation_successes_total{usecase,stream,status} را یکی زیاد می‌کند؛ برخلاف نامش، شکست‌ها را هم می‌شمارد (agentlib/utils/metrics/llm.py:15-46).
  • رکورد LLMMetrics به callbackهای REPORT_METRICS داده می‌شود (llm_stream.py:100-103). در aiva و ADCS هیچ‌کس callbackی ثبت نکرده، پس شمارش توکن هر فراخوانی محاسبه و دور ریخته می‌شود. شمارش توکن در EX به‌جای آن از ردیابی‌های Phoenix و متریک‌های vLLM می‌آید (P3، P4).

برچسب usecase

هر LLM یک usecase می‌گیرد که به‌عنوان برچسب متریک استفاده می‌شود. aiva مقدارهای react، guardrail، greeting را تنظیم می‌کند (aiva/chat/utils/agents.py:22-108).

نکته‌های پنهان

در این مسیر هیچ مهلت زمانی برای درخواست وجود ندارد. سرور مدلِ هنگ‌کرده تا 600 ثانیه برای هر تلاش نوبت را نگه می‌دارد، با 2 تلاش مجدد خودکار (از پیش‌فرض‌های SDK استنباط شده).
موتور سرویس‌دهی باید Responses API را پشتیبانی کند. vLLM پشتیبانی می‌کند؛ رفتن به سروری که فقط Chat Completions دارد به یک کلاس LLM جدید نیاز دارد (استنباطی).
