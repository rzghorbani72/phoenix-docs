How a model is chosen for a step

Nobody wrote the selection rules down, but the config shows a consistent pattern. Read it as four questions asked per step (inferred from how roles are distributed):

  1. Does a wrong answer reach the caller or block them? Main answer (ReAct) and guardrail use the strongest in-house model: dense Gemma-4 31B. Quality wins over speed.
  2. Is it a short decision taken on every turn? Intent, classify, clarify and end-of-turn are yes/no or pick-one tasks. They go to the MoE Gemma-4 26B-A4B: roughly 4B parameters of compute per token, so 3–6x faster decode than a dense 31B at similar knowledge (inferred).
  3. Is it a trivial filter over many items? The relevance filter runs on the smallest model, Gemma-4 E2B.
  4. Is there no employee data yet and quality of open talk matters? The greeting is the only EX LLM step sent to OpenAI (gpt-6-luna). Sister products (aiva, aiva-poll) send the whole main agent there; EX keeps it in-house (inferred: HR data residency).

Two more rules apply to all LLM steps: every model is reached through an OpenAI-compatible /v1 endpoint, so swapping a model is a two-line env change (*_LLM_BASE_URL, *_LLM_MODEL); and prompts come from the Phoenix prompt registry, not from git, so a model swap may need a matching prompt version.

Because a swap is only an env change, models move often: the EX ReAct agent changed model three times in three days (luna → 31B → 26B → dedicated 31B). Always check the timeline below before trusting a diagram.

What the numbers mean (MoE, active parameters, context caps)

  • Dense vs MoE. A dense model (Gemma-4 31B) uses all its weights for every token. A mixture-of-experts model (26B-A4B, gpt-oss-120b, Qwen A3B) holds many 'experts' but routes each token through a few. Memory follows total parameters; speed and cost per token follow active parameters.
  • Rule of thumb (inferred): decode speed on one GPU scales roughly with 1 / active parameters. 26B-A4B (~4B active) should generate tokens several times faster than 31B dense, if the batch is not memory-bound.
  • Context cap. --max-model-len sets the largest prompt + answer the server accepts. It is set far below native windows (15K or 23K vs ~256K) to keep KV-cache memory free for more parallel requests. A prompt that is too long fails with an HTTP 400, it is not silently trimmed.
  • Speculative decoding (MTP). Gemma-4 31B pods run a small draft model (/opt/models/mtp_model) that proposes 4 tokens at a time; the big model checks them in one pass. Same output, fewer slow steps.
  • Per-layer embeddings (E2B). Gemma-4 E2B stores a large share of its weights as per-layer embedding tables that can live outside fast GPU memory; only ~2B parameters are 'effective' compute.

Platform-wide risks a TPM should track

  • EX's main brain has no failover. The dedicated 31B is one IP:port with no Envoy, no health check and no Prometheus scrape. If that server restarts, every EX voice turn fails until it returns (inferred).
  • One host carries many pools. 172.23.0.17 serves the EX dedicated 31B (:8318), a 31B shared upstream (:8319), three COA upstreams, the zarebin pool, hakim-unsup, hakim-search, Qwen3.6 and gemma-embedding ports. A single machine fault affects many products (inferred: if these are one machine).
  • Model routing partly lives outside git. AxonHub aliases (main-guardrail etc.) resolve in a database; bare-metal vLLM flags (context caps, spec-decode) for 20+ upstreams are not in git.
  • Exporter gaps. Several live upstreams are not scraped and some scraped ones are mislabelled, so Grafana totals per model are incomplete. See each model page.
  • Data leaving the cluster. EX sends the greeting to OpenAI and caller audio to Soniox. Both go through envoy-relay-chatbot. Confirm this is acceptable for employee voice data.
