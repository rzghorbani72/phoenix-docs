Read it next to the pipeline map; it does not repeat the general AI course in the AI learning guide (Persian).

How to use this site

The site is built in layers. The map shows six lanes of boxes; each box opens a step page with the model, its size, inputs, outputs, settings, failure behaviour and code references. The Models page lists every model once, and Risks & gaps collects what a TPM should track. This guide is the glue: it teaches the vocabulary, gives you a reading order, and turns the pages into exercises and questions.

  1. The map first (index.html). Read the one-sentence summary and the “things to know” warning. Do not open any step yet; just learn the six lanes and the arrows between them.
  2. Lane 1, the phone call. This is what the employee experiences. Read V1 → V13 in order; it teaches VAD, speech-to-text, turn-taking and text-to-speech in the order they happen.
  3. Lane 2, the brain. One turn inside aiva. Read B1 (prompt loading) before anything else, then follow the orchestration: intent, clarifying, retrieval, guardrail, classifier, branch selection, ReAct.
  4. Lane 3, the knowledge base. Where approved HR answers come from and how they reach the prompt. This lane decides whether the agent is grounded.
  5. Lane 5, post-call analytics. What HR sees in the panel after the call, and which parts are a black box.
  6. Models. Now the sizes and roles make sense. Read it with section “How to reason about model choice” below.
  7. Risks & gaps. Read it last, when every risk points at a step you already know.
  8. The framework lane and the remaining lanes (memory, ops) as reference: return to them when a question touches data stores, serving or observability.
Status labels matter. Live, Configured-off, Not-deployed, External and Unverified are different claims. When you repeat something from this site to a stakeholder, keep its label: “the code supports human transfer” is not the same as “EX transfers calls”. Text marked (inferred) is reasoning, not code.

Two other documents are your companions. The EX PRD (Persian) says what the agent should do (rule ids like SEN, GRD, KB, CLO, VOX); this site says what it does. The AI learning guide (Persian) covers general AI background, benchmarks and Hugging Face reading; this guide only goes as deep as you need for EX.

A 10-day plan to proficiency

About 2–3 focused hours a day. Each day ends with a small artefact you keep (a note, a diagram, a list of questions), because writing is what turns reading into ownership. By day 10 you should be able to explain any EX turn end to end, name the model behind every decision, and run the pilot go/no-go conversation.

The system on one page

An employee calls a number. The call reaches a LiveKit server over SIP and is handed to a Python voice agent. The agent listens with Silero VAD, streams the audio to Soniox (a cloud speech-to-text service), asks a Gemma-4 26B-A4B model whether the employee has finished speaking, and then sends the text to aiva, the brain. aiva runs several small model calls in parallel (exit intent, a speculative short reply, retrieval with an E2B relevance filter, a route classifier and a 31B guardrail), then lets the Gemma-4 31B ReAct agent write the answer from approved HR knowledge. The streamed answer is spoken by the in-house neurobox TTS. After hang-up, the recording and a summary flow through Kafka to grogu, which re-transcribes the call, and to the external CCA engine, which tags it for the EX panel.

Concepts 1: how a language model works (just enough)

You do not need the maths. You need the handful of quantities that decide quality, speed, cost and failure modes of every LLM call in EX. For deeper background see the AI learning guide.

  • Token. Models do not read letters or words; they read tokens, chunks of text from a fixed vocabulary of tens of thousands of pieces. An English word is about 1.3 tokens; Persian usually costs more tokens per word because tokenizers were trained on less Persian text (roughly 1.5–3 per word, (inferred) for Gemma's tokenizer). Everything is counted in tokens: prompt size, answer size, speed, limits. In EX: every number on P4 metrics (vllm:prompt_tokens_total, vllm:generation_tokens_total) is tokens; the Kafka call summary carries token counts (V13).
  • Prompt vs completion. The prompt is everything sent in (system instructions, history, retrieved knowledge, the employee's words); the completion is what comes back. Reading the prompt is called prefill and is done in parallel, fast per token; writing the completion is decode, one token at a time, and is what you hear as speaking speed. In EX: the ReAct prompt is large (system prompt + up to 50 history items + up to 10 Q&A contexts) and its answer is short, so prefill dominates time-to-first-token (B10).
  • Context window vs deployed --max-model-len. The context window is the most tokens a model can handle at once (prompt + completion). The model card states a native maximum (very large for Gemma-4, on the order of 128K–256K); the deployment sets the real limit with vLLM's --max-model-len, because every token of possible context reserves GPU memory. In EX: the 31B pools run at 15K and the 26B-A4B pool at 23K (P1). Since today the ReAct agent runs on 31B, its budget may have shrunk from 23K to 15K if the dedicated instance uses the same flags (unverified: its flags are not in git). A request over the limit is rejected with an HTTP 400 and the turn fails; it does not silently truncate.
  • Parameters and “B”. Parameters are the learned numbers inside the model; “31B” means about 31 billion. More parameters usually means better reasoning and language quality, but also more GPU memory and slower decoding. Memory rule of thumb: in 16-bit precision each parameter takes 2 bytes, so 31B ≈ 62 GB of weights before any working memory. In EX: sizes per model are on Models; they are public model facts, not read from code.
  • Dense vs Mixture-of-Experts (MoE); total vs active parameters. A dense model uses all its parameters for every token. An MoE model has many “expert” sub-networks and a router that picks a few per token. 26B-A4B means 26B total, about 4B active per token; 35B-A3B (the Qwen3.5 code default for the KB summarizer, overridden in EX, see K2) means 35B total, 3B active. Why active params drive speed: decoding one token means reading every weight that participates from GPU memory, and memory bandwidth is the bottleneck. A4B reads ~4B weights per token, the 31B dense reads all 31B, so the MoE decodes several times faster on the same GPU. But all 26B must still fit in memory, so MoE saves time, not memory. In EX: this is why the latency-critical small decisions (V5, B4, B5, B8) use 26B-A4B, and why moving the ReAct agent to 31B dense costs speed.
  • Per-layer embeddings and “effective” size (E2B). Gemma-4 E2B stores a large share of its parameters in per-layer embedding tables, which are looked up rather than multiplied, so they can live in cheaper memory and add little compute. “E2B” = about 2B effective (compute-relevant) parameters, around 5B counting the embeddings. In EX: E2B is the relevance filter on every turn (K7, model); it is the smallest and fastest LLM in the stack, and also the one whose mistakes decide what knowledge the answer agent sees.
  • Quantization and dtype. Weights can be stored at lower precision: bf16 (2 bytes), fp8 (1 byte), int4 (half a byte). Lower precision means less memory and faster decode, with some quality loss, usually small at fp8 and more visible in non-English languages at 4-bit. In EX: no values file sets --dtype or --quantization, so the in-cluster pods use vLLM's default (bf16 for Gemma, (inferred)); the bare-metal instances' flags, including the new :8318, are not in git (P1). Ask SRE.
  • Temperature, max tokens, reasoning effort. Temperature controls randomness: 0 = always the most likely token (repeatable), higher = more varied. Max tokens caps the completion length. Reasoning effort tells “thinking” models how much hidden reasoning to produce before answering; more thinking = better on hard questions but more latency. In EX: intent runs at temperature 0.1 (a decision must be stable) (B4); the ReAct agent and greeting run with reasoning effort none and no explicit temperature or max tokens, so server defaults apply (B10, B2); the E2B filter allows up to 4096 output tokens for what is a short JSON list (K7).
  • Streaming, time-to-first-token (TTFT), tokens/sec. With streaming, tokens are sent as soon as they are generated. For a phone call the number that matters is TTFT (queue wait + prefill) plus the time to produce the first full sentence, because TTS needs a sentence before it can speak. Tokens/sec (decode speed) then decides whether the rest of the answer keeps up with speech. In EX: the ReAct agent and clarifying agent stream; intent, classifier, guardrail and greeting do not, so their full completion time is on the critical path. TTS waits for ". " before synthesising (V8), so a long first sentence delays audio.
  • Speculative decoding (MTP). A small, fast draft predicts several next tokens; the big model checks them all in one step and keeps the ones it agrees with. When the draft is often right, you get 1.5–2.5× faster decoding with identical output quality. Gemma-4 uses an MTP (multi-token prediction) draft. In EX: the shared 31B pool runs MTP with 4 speculative tokens; it is off on the 26B-A4B pool because of a vLLM 0.25.1 bug (P1). Whether the new dedicated :8318 instance runs MTP is a key latency question for today's change.

Concepts 2: how models are served

  • vLLM. The open-source inference server that runs every in-house LLM and the Hakim embedder here. It exposes an OpenAI-compatible HTTP API (/v1/chat/completions, /v1/responses, /v1/embeddings), which is why aiva can talk to Gemma and to OpenAI with the same client. In EX: version 0.25.1 on the main pools (P1).
  • Continuous batching. A GPU is most efficient when it processes many requests together. vLLM adds and removes requests from the running batch every step instead of waiting for a batch to finish, so a short request (an end-of-turn float) is not stuck behind a long one. The flip side: under heavy load every request slows down a bit, and queued requests wait. In EX: this is why the shared pools' load from other products shows up as EX latency; vllm:num_requests_waiting is the queue.
  • KV cache. While processing a request, the model keeps intermediate results (keys and values) for every token so it does not recompute them. This cache lives in GPU memory and grows with context length × concurrent requests. When it is full, new requests wait or running ones are pre-empted. Prefix caching lets requests that share the same beginning (for example, the same system prompt) reuse it. In EX: aiva renders the ReAct system prompt from cache-stable fields only so the prefix can be reused (B10); vllm:gpu_cache_usage_perc (or kv_cache_usage_perc) shows how full it is.
  • GPU memory utilization. --gpu-memory-utilization 0.95 lets vLLM take 95% of GPU memory: weights first, the rest for KV cache. With 31B in bf16 (~62 GB), what is left decides how many 15K-token conversations fit at once. This is the real reason context windows are set far below the native maximum: memory per concurrent call. In EX: all pools use 0.95 (P1).
  • Load balancers and bare-metal pools. Each model “pool” is an Envoy load balancer (*-llm-lb) in Kubernetes that spreads requests over one in-cluster vLLM pod and several bare-metal GPU servers (172.16.21.4, 172.23.0.3/.4/.17 on various ports). Envoy retries on unhealthy upstreams and exports per-pool latency. In EX: the 26B-A4B pool is shared by 11 services and the 31B pool by 17; the new dedicated 172.23.0.17:8318 is a single upstream with no load balancer in front (as described in the change), so it has no failover and its metrics are not scraped unless SRE adds it to the exporter (inferred) (P1, P4).
  • Gateways (AxonHub). A gateway maps aliases like main-guardrail to real models in a database. Useful for operators, opaque for reviewers. In EX: only one disabled step uses it (P2).

Concepts 3: retrieval and grounding

  • Embedding / vector. An embedding model turns a text into a list of numbers (a vector) so that texts with similar meaning get nearby vectors. In EX: hakim-unsup, an in-house Persian encoder (~0.12B), produces 768-number vectors (K4).
  • Cosine similarity. A score for how closely two vectors point the same way: 1 = same meaning, 0 = unrelated. It is a ranking signal, not a probability, and each embedding model has its own scale: 0.25 on Hakim is not comparable to 0.25 on another model.
  • Multivector and MAX_SIM. Instead of one vector per answer, EX stores one vector per paraphrase question (an N×768 multivector per answer). At query time the answer's score is the maximum similarity between the query and any of its questions (Qdrant MAX_SIM). Effect: adding a new paraphrase can only help an answer be found; it never dilutes the others. In EX: K5 collections.
  • Threshold and top-k. Top-k = how many best matches to keep (10 here); threshold = minimum similarity (0.25 here, code default 0.5). Low threshold → high recall (rarely misses the right answer) but more noise; high threshold → precise but misses paraphrases. In EX: the low bar deliberately pushes precision onto the E2B filter (K6).
  • RAG (retrieval-augmented generation). Instead of trusting what the model memorised, you retrieve approved text and put it into the prompt, and instruct the model to answer only from it. In EX: retrieved Question:/Answer: pairs fill {contexts} in the ReAct user template (K8). Grounding is only as good as retrieval: if the right Q&A is not retrieved, the model either says it does not know or, worse, improvises.
  • Why only questions are embedded. An employee's utterance looks like a question, not like a long policy answer. Matching question-to-question is more precise than question-to-answer, so EX embeds only the paraphrase questions (K4). The product consequence: coverage = paraphrase coverage. If HR writes one phrasing per answer, many real spoken phrasings will miss. Only the latest utterance is embedded, with no rewriting, so short follow-ups like «اون یکی چی؟» rely on carry-over (K6, K8).
  • LLM relevance filter vs reranker. A reranker is a model (often a cross-encoder) that scores each (query, candidate) pair and re-orders them; it outputs scores. An LLM filter reads the whole conversation plus the candidate list and returns which items to keep. It understands context better but is slower, can produce invalid output and needs a failure policy. In EX: the filter is Gemma-4 E2B with prompt ex_iva_contexts_filter_llm_template, returning {"indexes":[…]}; on any error it fails open and passes all candidates unfiltered (K7).
Grounding in EX is prompt-only. There is no code rule “no relevant context → refuse”. The chain threshold 0.25 → E2B filter (fails open) → 31B ReAct prompt instruction is what keeps answers inside the KB. Test it with questions the KB does not cover.

Concepts 4: agents, guardrails and prompts

  • Guardrail. A separate check that decides whether a request may be handled, before or alongside the answer. It can be a rule, a classifier or an LLM. In EX: the B7 guardrail is a Gemma-4 31B call that reads the conversation, the filtered contexts and retrieved allow/deny policies (from chatbot-ex-aiva-guardrails) and replies 1 (allow) or 0 (deny). A deny replaces the answer with a generated polite refusal (B12).
  • Fail-open vs fail-closed. When a safety component fails (timeout, error, garbage output), fail-open lets the request through; fail-closed blocks it. Fail-open protects availability, fail-closed protects safety. Neither is “right”; it is a product decision per component. In EX: the guardrail (empty or non-numeric reply = allowed), the relevance filter (error = all candidates pass) and intent (error = continue) all fail open; the end-of-turn detector fails to “finished” (V5). Write down which of these HR would accept.
  • ReAct and tool calling. ReAct (Reason + Act) is an agent loop: the model either answers or asks to call a tool (a function with a name and JSON arguments); the system runs the tool and gives the result back; repeat until an answer. Tool calling is the model emitting a structured call instead of text. In EX: the B10 ReAct agent may loop up to 10 times, but its only enabled tool is send_sms, without a token (B11); ending the call is a separate intent agent with exit_tool.
  • Intent detection and routing / classification. Intent detection asks “what does the user want to do?” (here: hang up or continue). Routing picks which agent should answer (here: main or clarifying_chitchat). Both are classification tasks: short output, best done by a fast model at low temperature, with a safe default when the output is invalid. In EX: B4 intent, B8 classifier (invalid → main). Note the classifier's few-shot examples come from a shared, non-EX collection.
  • Speculative branches and cancellation. To hide latency, aiva starts several possible answers before it knows which one it needs, and cancels the losers. In EX: the clarifying reply streams privately on every turn; the orchestrator picks guardrail-deny > exit > clarifying > main and cancels the rest (B9). Cost: GPU work on every turn for output that is usually thrown away; benefit: short social replies feel instant.
  • Prompt registry and prompt versioning. Prompts are product logic. A registry stores each prompt with versions and tags so you can change and roll back wording without a code release. In EX: aiva loads 13 ex_iva_* prompts from Phoenix with tag production, once at pod start (B1, P3). Editing in Phoenix is a production change without code review, and it takes effect only after a restart. The model shown next to a prompt in Phoenix is ignored; since today the main and guardrail prompts happen to match it (31B), the others still do not.
PRD link. The PRD's decision order (listen first, one follow-up at most, KB-only answers, sensitive-topic handling, no promises about pay or promotion) is implemented only inside the Phoenix prompt text and the ReAct model's obedience to it. That is why the 31B upgrade matters and why prompt versions must be governed. See the EX PRD.

Concepts 5: voice

  • VAD (voice activity detection). A tiny model that says, every few milliseconds, “speech” or “not speech”. It is the clock of the conversation: end of speech, barge-in and the silence timer all start from it. In EX: Silero VAD at threshold 0.3 and 0.2 s minimum speech: sensitive, to catch a short «بله» (V3).
  • STT / ASR (speech-to-text / automatic speech recognition). Turns audio into text. Streaming ASR returns partial (interim) text while the person talks and a final text shortly after they stop; it must be fast and is usually slightly less accurate. Offline ASR gets the whole file and can use full context, so it is more accurate and can add labels (emotion, gender, speaker channel). In EX: live = Soniox, cloud, external (V4); after the call = in-house k2 ASR coa_iva_prod_long (A3). The two transcripts can differ, so the analysed text is not exactly what the bot heard.
  • WER (word error rate). The standard ASR quality metric: (substituted + deleted + inserted words) ÷ words in the reference transcript. 10% WER means roughly one word in ten is wrong. For Persian, measure on your own audio (accents, phone line quality, HR vocabulary); vendor numbers rarely transfer. In EX: no WER measurement exists in the repos; a labelled sample of pilot calls is the only way to compare Soniox vs k2 fairly.
  • End-of-turn detection. Deciding that the person has finished their thought, not just paused. Silence alone is a poor signal in Persian («که…» trails off mid-thought). In EX: after 0.5 s of silence a Gemma-4 26B-A4B call reads the last 6 messages and returns a probability; below 0.5 the agent waits longer (V5).
  • Endpointing. The extra wait between “probably finished” and committing the turn to the brain. Too short cuts people off; too long feels robotic. In EX: dynamic 0.1–0.5 s, about 5× tighter than the defaults (V6).
  • Barge-in. Letting the caller interrupt the agent: playback stops when the caller speaks long enough. In EX: 0.4 s of VAD speech (V9); with a sensitive VAD, line noise can cut the agent off.
  • TTS (text-to-speech). Turns text into audio. Most TTS needs a full sentence for natural prosody, so the text stream is split into sentences first. In EX: neurobox ex_prod, speed 1.1; the splitter breaks only on ". ", so a Persian question ending in ؟ is synthesised as one long chunk (V8).
  • Thinking sound and voice bridge. Ways to mask the gap while the brain works: an ambient sound (on in EX) or a generated filler sentence (the voice bridge, off in EX) (B13).

Concepts 6: data pipelines and observability

  • Kafka. A durable message log. Producers append messages to a topic; consumers read at their own pace and record their position (offset). It decouples the live call from slow post-call work. In EX: the voice agent publishes to chatbot-mci-ex-iva (V13); grogu publishes to anzu-coa-call-ex for CCA (A4).
  • At-least-once delivery. The consumer commits its offset only after the work is safely recorded, so after a crash a message may be processed twice but never lost. Consumers must therefore be idempotent (safe to repeat). In EX: grogu commits after the DB rows exist and skips calls already in progress or done (A1). Note the producer side: a failed summary publish is logged, not re-queued, so a call can be missing from analytics entirely.
  • Dead letters. Messages that failed processing are parked in a dead-letter store and retried later instead of blocking the stream. In EX: grogu's dead-letter table is retried every 5 min, up to 10 times (A1). A call that never succeeds needs a human to notice it: ask who owns that alert.
  • ClickHouse vs Postgres. Postgres is a transactional database: row-by-row reads and writes, constraints, good for the app's own state (sessions, messages, KB). ClickHouse is a columnar analytics database: very fast aggregation over millions of rows, append-oriented, poor at single-row updates. In EX: CCA writes results to ClickHouse zaal.ex_call_analytics_dist; sync daemons copy them into Postgres coa_ex for the panel (A6, A7).
  • Tracing (OpenTelemetry / OpenInference). A trace is the tree of operations (spans) for one request, each with timing and attributes. OpenTelemetry is the general standard; OpenInference is its LLM flavour (spans for LLM calls, retrievers, tools, with prompts and outputs). In EX: aiva sends 100% of IVA traces to Phoenix project chatbot-ex-iva, kept 30 days (P3). Traces contain employee text and phone numbers, so they are also a privacy store (M4).
  • Metrics (Prometheus). Numbers sampled over time (counters, gauges, histograms) scraped from /metrics endpoints and queried with PromQL in Grafana. Metrics tell you how much and how fast for a whole pool; traces tell you why for one request. In EX: vLLM and Envoy series per pool (P4); they cannot separate EX from the other products on a shared pool. The dedicated :8318 endpoint is the first EX-only LLM, so its metrics would be EX-only, if it is scraped.

How to reason about model choice for a step

Every LLM step is a trade-off between five forces. Ask them in this order, because on a phone call latency is a hard wall and privacy is a hard rule, while quality and cost are dials.

  1. Privacy and data residency. Does the input contain employee speech, identity or HR content? If yes, the default is in-cluster. EX has two exceptions today: Soniox (live audio) and OpenAI (greeting). Each needs explicit sign-off.
  2. Latency budget. Is the step on the critical path of a live turn, and is its output streamed? A non-streamed decision on the critical path must finish in a few hundred milliseconds; a streamed answer needs a low time-to-first-sentence. Offline steps (KB summarizer, CCA) can be slow.
  3. Task difficulty and quality. Classification and picking from a list are easy (small or MoE model); following a long rule-heavy Persian prompt with sensitive-topic rules is hard (largest model). Measure, do not guess: build a small labelled test set per step.
  4. Cost and capacity. Calls per turn × turns per call × concurrent calls. A call that runs on every turn and is often thrown away (clarifying) costs as much as one that is always used.
  5. Failure behaviour. What happens on timeout or bad output, and is the pool shared? A shared pool imports other products' load spikes into your latency; a dedicated endpoint removes that but adds a single point of failure.

Reading the table. About 3.5 s of silence (filled by the thinking sound) before the answer starts, of which ~0.9 s is the voice layer and the rest is the brain and TTS (inferred). The critical path is: VAD → end-of-turn → endpointing → embedding → Qdrant → E2B filter → 31B guardrail → 31B ReAct prefill + first sentence → TTS. Intent, classifier and clarifying run in parallel and only matter if they are slower than that chain. Before today, ReAct on 26B-A4B would likely have started speaking a few hundred milliseconds earlier (inferred); the guardrail, now on a quiet dedicated instance, may be faster than it was on the busy shared pool. Measure both in Phoenix traces.

Where it goes wrong. If the answer has no ". " in its first sentence (Persian often ends with ؟ or no period), TTS waits for the whole answer. If the E2B filter fails, all 10 candidates pass and the 31B must ignore the irrelevant ones. If :8318 is slow, both guardrail and answer wait; the voice agent gives up after 10 s × 3 retries. If this were a goodbye, intent would emit exit and the call would end without the guardrail or ReAct being used.

After hang-up (lane 5): the agent publishes the session summary to Kafka chatbot-mci-ex-iva (V13); grogu merges the two .ogg tracks into stereo (A2), re-transcribes with k2 ASR plus emotion and gender (A3), publishes to anzu-coa-call-ex (A4); CCA writes tags, sentiment and a summary to ClickHouse (A5); sync daemons copy them to Postgres (A7), and HR sees the call in the EX panel minutes later (inferred) (A9).
