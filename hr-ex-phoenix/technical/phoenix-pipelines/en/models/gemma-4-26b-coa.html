Gemma-4 26B-A4B · COA pool

Unverified 26B total · ~4B active · 23K context

In one paragraph for a TPM: a second, separate 26B-A4B deployment with two Kubernetes replicas and its own load balancer, built for COA (the call-analytics stack). It runs an older vLLM (0.23.0) that still has speculative decoding enabled, so it may actually be faster per request than the shared 26B pool. No service in git calls it by name; the CCA analysis engine is the likely user (inferred).

How it is served here

Same flags as the shared pool except engine version and spec-decode. Added 2026-06-03 (d9f6f3209 “add gemma4-26b-coa Helm chart and configuration”). The Envoy has custom latency histogram buckets 10 ms–300 s (:247-264) and JSON access logs (:286-310).

Who uses it

No reference outside its chart. Likely CCA tagging of recorded calls (AI analysis engine) (inferred). mci-agentic's coa-api uses 26B for USER_INFO_MCI_LLM_MODEL but through the shared LB.

Why it exists (inferred)

Cheap MoE throughput for batch analytics, isolated from live traffic, with the engine version that still supports MTP for Gemma-4 26B.

Trade-offs

  • Two engine versions for the same model (0.23.0 here, 0.25.1 shared) mean different bugs and features: tool-call parsing may differ.
  • Two dedicated pods are expensive if idle.

Risks and open questions

  • Owner and utilisation unknown.
  • Upgrade path: moving to 0.25.1 would lose spec-decode until the vLLM bug is fixed.

How to observe it

  • ServiceMonitor on the pods (/metrics, 15 s) and on the Envoy admin port (30 s, :179-183).
  • Envoy access log tag gemma4-26b-coa-llm-lb-prod.chatbot reveals caller IPs.
