Gemma-4 26B-A4B · shared pool (gemma4-26b-llm-lb)

Live 26B total · ~4B active (MoE) · 23K context here

In one paragraph for a TPM: Gemma-4 26B-A4B is a mixture-of-experts model: it stores ~26B parameters but uses only about 4B for each token. That makes it nearly as knowledgeable as a large model but several times faster and cheaper per token than the dense 31B. EX uses it for every quick decision in a voice turn: has the caller finished speaking, does the call need to end, does the request need clarifying, which branch should answer. Until today it also ran the main EX answer agent. It has the largest context cap in the platform (23,000 tokens), but speculative decoding is switched off on the k8s pod because of a vLLM bug.

What it is (model facts)

A sparse MoE member of Gemma-4. A router picks a few experts per token, so compute per token is ~4B parameters while the full ~26B must sit in GPU memory. Native multimodal input (text + image); here text-only. 'A4B' = about 4B active.

EX steps: end-of-turn, intent, clarify, classify, voice bridge, signal turns.

Why it is used there

Each of these steps runs on every turn, often several in parallel, before the caller hears anything. They are short classification-style prompts, so a ~4B-active model gives enough judgement while keeping the turn fast (inferred). Commits 62c1f34ab and 220cf41ea (Oct 14–17) moved several bots “from old gpt oss model urls to new gemma4 26b”, making 26B-A4B the platform's default fast model.

Code note: the LiveKit agent's own default for turn detection is the 31B (phoenix:python/chatbot-iva-agent/src/config.py:105); EX overrides it to 26B. Turn modes are mci, openai, deactive (src/enums.py:21-24).

Trade-offs

  • Speed vs depth: fast and cheap, but weaker than 31B on multi-step reasoning; EX moved its main agent off 26B after two days (inferred: quality).
  • 23K cap is the most generous in the platform; prompts that fit here may not fit on the 31B (15K).
  • No spec-decode on the k8s pod: one of the speed levers is off until vLLM is fixed; the COA 26B pod (vLLM 0.23.0) still has it on.

Risks and open questions

  • CLARIFYING_LLM_* is defined twice in EX values; the later one wins. Same value today, drift risk.
  • Exporter scrapes 172.16.21.4:8220/8221 (not in the LB) as 26B; check labels in Grafana.
  • Is spec-decode on for the two bare-metal upstreams? Not visible.

How to observe it

  • Prometheus job vllm-gemma4-gpu-exporter (bare-metal 8225/8226) + pod ServiceMonitor; Envoy stats on the LB.
  • Phoenix chatbot-ex-iva: spans for intent / classify / clarify carry llm.model_name = google/gemma-4-26B-A4B-it.
  • Turn-detection latency also in Elastic APM from the LiveKit agent.
