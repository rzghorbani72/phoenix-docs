۲. چرا صدا روی UDP است نه TCP

در مکالمه زنده، بسته‌ای که با ۲۰۰ms تأخیر برسد دیگر به درد نمی‌خورد. در TCP یک بسته گم‌شده تا ارسال مجدد، همه بسته‌های بعدی را هم نگه می‌دارد (Head-of-Line Blocking) و صدا ثانیه‌ای قطع می‌شود و بعد فشرده می‌رسد. در UDP همان بسته گم‌شده فقط یک «پَر» کوتاه (۲۰ms) در صدا می‌سازد و مکالمه ادامه می‌دهد. برای همین در RTP گم‌شدن را می‌پذیریم و با Jitter Buffer، نوسان زمان رسیدن را صاف می‌کنیم.

۵. NAT (Network Address Translation) — چرا دشمن شماره‌یک صدا است

NAT آدرس خصوصی داخل شبکه (مثلاً 10.x.x.x) را موقع خروج به آدرس عمومی/دیگر تبدیل می‌کند و برای برگشت، جدول «چه کسی کدام اتصال را باز کرد» نگه می‌دارد. انواع رایج: SNAT (تغییر آدرس مبدأ برای خروج)، DNAT (تغییر آدرس مقصد برای ورود، مثل Port Forward) و PAT (چند دستگاه با یک IP عمومی و پورت‌های متفاوت). برای وب و API بی‌ضرر است؛ برای VoIP مشکل‌ساز است چون:

  1. SIP آدرس را داخل متن پیام می‌برد. IP و پورت صدا در بدنه SDP (خط c= و m=) و در Header‌های Via و Contact نوشته می‌شود. NAT فقط Header بسته IP را عوض می‌کند، نه متن SIP را؛ پس طرف مقابل صدا را به آدرس خصوصی می‌فرستد که از بیرون قابل‌دسترس نیست → «تماس وصل شد ولی صدا نیست» یا «صدا یک‌طرفه است».
  2. RTP روی UDP است و «اتصال» ندارد. NAT یک «سوراخ» موقت برای هر جریان باز می‌کند و اگر مدتی (معمولاً ۳۰s تا چند دقیقه) بسته‌ای عبور نکند آن را می‌بندد. سکوت طولانی کاربر یا Hold می‌تواند صدا را قطع کند.
  3. پورت صدا پویا است. هر تماس پورت RTP تازه دارد (در SDP توافق می‌شود)، پس نمی‌توان یک قانون ثابت DNAT برای آن نوشت.

۶. Firewall و ACL (Access Control List) — چه چیزی باید باز باشد

Firewall بسته‌ها را بر اساس مبدأ، مقصد، پورت و پروتکل اجازه یا رد می‌کند. دو نوع: Stateless (هر بسته جدا بررسی می‌شود؛ هر دو جهت باید صریح باز باشد) و Stateful (اتصال را دنبال می‌کند و بسته برگشتی را خودکار اجازه می‌دهد). برای TCP حالت اتصال روشن است؛ برای UDP Firewall فقط یک «جریان موقت» با Timeout می‌سازد. ACL (Access Control List) فهرست ساده Allow/Deny روی Router و Switch است.

واژه‌نامه

اصطلاح معنا
IDOR — Insecure Direct Object Reference Insecure Direct Object Reference — دسته‌ای از آسیب‌پذیری Access Control؛ سرور یک شناسه (مثل call_id یا نام فایل) را از کاربر می‌گیرد و بدون بررسی اینکه آن رکورد واقعاً متعلق به همان کاربر/دسترسی اوست، مستقیماً آن را واکشی می‌کند. نمونه در این سند: GET /api/v1/files?name=<call-id>.wav با تغییر call-id، فایل صوتی تماس دیگران قابل دانلود است.
VAD — Voice Activity Detection Voice Activity Detection — الگوریتمی (معمولاً یک مدل سبک) که به‌صورت لحظه‌ای روی جریان صوتی اجرا می‌شود و فریم‌های حاوی گفتار را از سکوت/نویز پس‌زمینه جدا می‌کند. خروجی VAD ورودی مرحله‌ی Turn Detection است و در معماری Agent صوتی (LiveKit) پیش از ASR اجرا می‌شود.
Turn Detection / Endpointing منطقی که روی خروجی VAD (و گاه سیگنال‌های زبانی) تصمیم می‌گیرد کاربر نوبت صحبت خود را تمام کرده و اکنون نوبت پاسخ Agent است. تشخیص زودهنگام باعث قطع‌شدن وسط جمله‌ی کاربر می‌شود و تشخیص دیرهنگام باعث تأخیر محسوس در پاسخ Agent؛ تنظیم آن یک Trade-off مستقیم روی تجربه‌ی مکالمه است.
Barge-in قابلیتی که به کاربر اجازه می‌دهد وسط صحبت (TTS) Agent حرف بزند و Agent را متوقف کند — رفتار طبیعی مکالمه‌ی انسانی. در کد این پروژه با فلگ‌هایی مثل allow_interruptions در chatbot-iva-agent/src/agents/agentlib.py و entrypoint.py کنترل می‌شود (مثلاً در حالت‌های خاص مثل پیام خوش‌آمدگویی یا سکوت کاربر، Interruption غیرفعال می‌شود).
Egress در LiveKit، فرایند خروج/ضبط محتوای یک Room (صدا/تصویر Real-time) به یک فایل یا Stream خارجی (مثل ذخیره در Object Storage). در این پروژه برای ضبط ترک صدای کاربر و Agent (participant_track_path, agent_track_path) استفاده می‌شود تا بعداً برای ASR آفلاین یا Audit در دسترس باشد.
RAG — Retrieval-Augmented Generation Retrieval-Augmented Generation — الگویی که قبل از فراخوانی LLM، اسناد مرتبط از یک پایگاه دانش (Vector DB / Knowledge Base) بازیابی و به‌عنوان Context به Prompt اضافه می‌شوند، تا پاسخ مبتنی بر داده‌ی واقعی سازمان باشد نه فقط دانش از‌پیش‌آموخته‌ی مدل. کاهش Hallucination و امکان به‌روزرسانی دانش بدون Fine-tune از مزایای اصلی آن است.
ReAct الگوی طراحی Agent (Reason + Act) که در آن مدل به‌صورت تکرارشونده بین «استدلال درباره‌ی قدم بعدی» (Reason)، «اجرای یک Tool/Action» (Act) و «مشاهده‌ی نتیجه» (Observe) حرکت می‌کند تا به پاسخ نهایی برسد؛ پایه‌ی بسیاری از فریم‌ورک‌های Agentic از جمله ساختار Tool-calling در این پروژه.
SSE — Server-Sent Events Server-Sent Events — یک پروتکل HTTP تک‌جهته (سرور به کلاینت) که روی یک Connection باز، رویدادهای متنی را پشت‌سرهم Push می‌کند؛ در این پروژه برای Stream کردن تدریجی پاسخ LLM (Token-by-token) به کلاینت Chat استفاده می‌شود، بدون نیاز به WebSocket کامل.
DLQ — Dead Letter Queue Dead Letter Queue — یک صف جداگانه (روی Kafka/RabbitMQ) که پیام‌هایی را نگه می‌دارد که پردازش‌شان بارها Fail شده و Consumer اصلی نتوانسته آن‌ها را کامل کند؛ به‌جای گم‌شدن یا Retry بی‌نهایت پیام، امکان بررسی دستی/Replay بعدی را فراهم می‌کند.
Circuit Breaker الگوی مقاوم‌سازی سرویس: وقتی فراخوانی یک وابستگی بیرونی (مثل سرویس ASR) پی‌درپی خطا می‌دهد، Circuit Breaker به‌طور موقت مسیر فراخوانی را «باز» (Open) می‌کند تا درخواست‌های جدید بلافاصله Fail شوند و به سرویس خراب فشار نیاورند؛ بعد از یک بازه‌ی زمانی دوباره تست می‌کند (Half-Open) و در صورت موفقیت مسیر را می‌بندد. پیاده‌سازی آن در golang/grogu/internal/circuitbreak و استفاده‌اش در golang/grogu/internal/asr/service.go است.
MCP — Model Context Protocol Model Context Protocol — یک استاندارد باز برای اتصال مدل‌های زبانی به Tool ها/منابع داده‌ی بیرونی به‌شکل یکنواخت (سرور MCP قابلیت‌ها را اعلام می‌کند، مدل/Agent آن‌ها را فراخوانی می‌کند)، به‌جای اینکه هر Integration به‌صورت Ad-hoc و اختصاصی نوشته شود. در این پروژه agentlib-plugin-mcp این نقش را ایفا می‌کند.
WER — Word Error Rate Word Error Rate — معیار استاندارد دقت ASR: نسبت مجموع کلمات جایگزین‌شده (Substitution)، حذف‌شده (Deletion) و اضافه‌شده (Insertion) در متن پیاده‌شده به تعداد کل کلمات متن مرجع. WER پایین‌تر یعنی Transcript دقیق‌تر؛ مکمل معیار transcript_confidence که در سطح هر Utterance در Schema این پروژه ذخیره می‌شود.
سرشماره (Service Number) شماره کوتاه/خاصی که مشتری برای ورود به یک سرویس می‌گیرد. تخصیص آن فقط یک شناسه ورود است؛ تا Routing، اتصال، SBC و SIP Trunk آماده نشوند سرویس قابل استفاده نیست.
Zone / Core Network (شبکه مرکزی اپراتور) بخش مرکزی شبکه اپراتور که تماس را کنترل و Route می‌کند؛ تصمیم می‌گیرد تماس به یک سرشماره به کدام Trunk/مقصد برود.
Signaling پیام‌های کنترلی برقراری، تغییر و پایان تماس (چه کسی، به کجا، آزاد است یا نه، برقرار شد یا قطع). جدا از خود صدا (Media).
Backbone شبکه اصلی و پرظرفیت انتقال اپراتور (فیبر + تجهیزات Core) که Zoneها و دیتاسنترها را به هم وصل می‌کند. «وصل شدن به Backbone» یعنی Connectivity + Routing + IP + Security، نه فقط کابل.
VLAN / ACL / QoS — Virtual Local Area Network / Access Control List / Quality of Service VLAN: جداسازی منطقی شبکه روی یک زیرساخت فیزیکی. ACL: فهرست مجاز/ممنوع ترافیک بر اساس IP/پورت. QoS: اولویت‌دادن به ترافیک صدا (مثلاً DSCP EF) تا Jitter و Loss کم شود.
SBC — Session Border Controller Session Border Controller — دروازه امنیتی و کنترلی تماس‌های SIP در مرز شبکه: کنترل Session، امنیت، NAT Traversal، Topology Hiding، محدودسازی ظرفیت و Normalization پیام‌ها. معمولاً SIP Trunk اپراتور روی آن خاتمه می‌یابد.
SIP — Session Initiation Protocol Session Initiation Protocol (RFC 3261) — پروتکل Signaling تماس صوتی روی IP با پیام‌هایی مثل INVITE، 180 Ringing، 200 OK، ACK، BYE، OPTIONS و MESSAGE. خودش صدا را حمل نمی‌کند.
SIP Trunk (Session Initiation Protocol Trunk) ارتباط منطقی SIP بین دو سیستم (مثلاً اپراتور و SBC) با IPهای Peer، Transport، سقف کانال هم‌زمان و فرمت شماره توافق‌شده.
RTP — Real-time Transport Protocol Real-time Transport Protocol — حمل خود صدا (Media) روی UDP، معمولاً در بسته‌های ۲۰ms. مسیر آن ممکن است با مسیر SIP متفاوت باشد.
SDP — Session Description Protocol Session Description Protocol — بدنه پیام‌های SIP که IP، پورت و Codecهای Media را مذاکره می‌کند (Offer در INVITE، Answer در 200 OK). IP اشتباه در SDP علت رایج «صدا نمی‌آید» است.
Codec (G.711 — ITU-T standard; PCMA/PCMU) الگوریتم کدگذاری صدا. G.711 (PCMA/PCMU) استاندارد رایج تلفن: ۸ kHz، ۶۴ kbps خالص (~۸۷ kbps با Overhead). STT در IVA با همین صدای Narrowband کار می‌کند.
Jitter / Packet Loss (نوسان تأخیر / گم‌شدن بسته) Jitter: نوسان زمان رسیدن بسته‌های RTP؛ Packet Loss: بسته‌های گم‌شده. هر دو صدای تکه‌تکه/رباتیک و افت دقت STT ایجاد می‌کنند.
NAT Traversal — Network Address Translation Traversal مسئله عبور SIP/RTP از NAT: آدرس داخلی که در SDP/Via نوشته شده از بیرون قابل دسترسی نیست؛ نتیجه‌اش صدای یک‌طرفه یا قطع تماس بعد از ~۳۲ ثانیه است. SBC معمولاً آن را حل می‌کند.
LiveKit SIP / Dispatch پل LiveKit که تماس SIP را به یک Room تبدیل و Caller را با Identity sip_+98… Participant می‌کند؛ Dispatch Rule تعیین می‌کند کدام Agent Worker تماس را بگیرد. Headerهای SIP به‌شکل sip.h.* در Attributeهای Participant می‌آیند.
SIP MESSAGE (Redirect) — Session Initiation Protocol MESSAGE روش انتقال به کارشناس در Phoenix: به‌جای REFER استاندارد، sip-messager یک پیام MESSAGE با X-Resolution و X-Destination (پیش‌فرض 6040) به Hop استخراج‌شده از Via می‌فرستد و انتظار 202 دارد.
HA / Failover — High Availability High Availability: چند Node/دیتاسنتر تا خرابی یکی سرویس را متوقف نکند. Failover: انتقال خودکار ترافیک به Node سالم.
Concurrent Calls (تماس‌های هم‌زمان) تعداد تماس‌های هم‌زمان — واحد اصلی ظرفیت: هر تماس هم‌زمان یک SIP Session، دو جریان RTP، یک Agent Job و یک Session هم‌زمان STT/LLM/TTS مصرف می‌کند.
Fine-tuning آموزش مجدد پارامترهای یک مدل از‌پیش‌آموزش‌دیده روی دیتاست مشخص تا رفتار، لحن یا یک Task خاص را بهتر یاد بگیرد. برخلاف RAG برای دانش متغیر (قیمت، رویه) مناسب نیست. RAG و Fine-tuning می‌توانند با هم باشند: RAG دانش را می‌دهد، Fine-tuning رفتار را تنظیم می‌کند. در Phoenix کد Fine-tuning وجود ندارد.
k-anonymity یک مدل حریم‌خصوصی آماری: داده یا آمار تجمیعی فقط زمانی نمایش داده می‌شود که حداقل k رکورد/فرد پشت آن گروه باشند، تا نتوان با ترکیب فیلترها یک فرد خاص را از داخل گروه شناسایی کرد (مثلاً جلوگیری از نمایش «Sentiment منفی» برای گروهی با فقط ۲ نفر که عملاً هویت را لو می‌دهد). در این سند به‌عنوان مکانیزم Suppression گروه‌های کوچک (PRV-05) به‌کار رفته.
