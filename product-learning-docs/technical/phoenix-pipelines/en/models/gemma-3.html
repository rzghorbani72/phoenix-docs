Gemma-3 12B and 27B (legacy pools)

Live 12B and 27B dense · 15K context (12B pod)

In one paragraph for a TPM: the previous Gemma generation still serves a handful of older MCI chatbots. The 12B has a small Kubernetes deployment plus two bare-metal processes; the 27B exists only on bare metal, and its load balancer is scaled to zero, so bots reach it by raw IP. Nothing in EX uses Gemma-3. The main TPM question is when these bots migrate, so the GPUs can be freed.

Why it is used there (inferred)

Bots built before Gemma-4 were tuned on Gemma-3 prompts; migrating needs prompt re-testing.

Trade-offs

  • vLLM 0.11.0 is many versions behind (0.25.1 elsewhere): no Gemma-4 parsers, older scheduling.
  • Raw-IP callers bypass any LB health check.

Risks and open questions

  • Callers of gemma3-27-llm-lb get connection errors if the LB really has 0 pods (unless they have a fallback) — verify those bots are actually live.
  • Exporter scrapes only 172.16.21.4:7001 for 12B.

How to observe it

  • vllm-gemma3-12-gpu-exporter (bare-metal 7001) and the 12B pod ServiceMonitor.
