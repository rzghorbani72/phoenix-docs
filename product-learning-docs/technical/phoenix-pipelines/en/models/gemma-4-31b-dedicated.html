Gemma-4 31B · EX dedicated server (172.23.0.17:8318)

Live 31B dense · context cap unknown (not in git)

In one paragraph for a TPM: since today (2026-11-02) the two most important LLM calls in an EX voice call — the main answer agent that decides what to say and which tool to call, and the guardrail that blocks unsafe or off-topic requests — both go to one Gemma-4 31B server reserved for EX. Before today they shared pools with ~17 other services. The upside is predictable latency and the best in-house answer quality. The downside is that this server is a single bare-metal process addressed by IP: no load balancer, no automatic failover, and no Prometheus scrape, and its context limit and flags are not recorded in git.

What it is (model facts)

Gemma-4 31B is the largest dense member of Google's open Gemma-4 family. 'Dense' means every one of its ~31 billion parameters is used for every generated token, which is why it is the slowest and the strongest Gemma-4 variant in this platform. The model natively accepts text and images and has a long native context window (reported ~256K tokens). These facts are general knowledge, not read from code; check the model card before quoting them externally.

Why it is used here

Commit b7e5664e3 (y.fallah, 2026-11-02): “chore(chatbot-ex): move the main & guardrail llm to dedicated gemma31”. A follow-up dd851385e “change llm model name” switched AGENT_LLM_MODEL from google/gemma-4-26B-A4B-it to google/gemma-4-31B-it, because the dedicated server only serves the 31B name. Between those two commits the agent sent a 26B model name to a 31B server, which vLLM would reject as an unknown model (inferred).

Why dedicated, not the shared pool (inferred): the shared gemma-4-31b-llm-lb serves ~17 services; queueing behind MCI IVA traffic would add unpredictable latency to every EX turn. Why 31B, not 26B: on 2026-10-31 the agent was moved from 31B to 26B-A4B (aa7c46605) and two days later back to 31B, which suggests 26B answer quality was not acceptable for EX (inferred).

Trade-offs

  • Latency. 31B dense computes ~7–8x more parameters per token than 26B-A4B's ~4B active. Expect slower token generation per reply unless the server runs MTP spec-decode (unknown here) (inferred).
  • Quality. Dense 31B is the strongest self-hosted model for Persian reasoning and tool choice (inferred).
  • Cost. A whole GPU server for one product's two steps. Utilisation depends only on EX call volume (inferred).
  • Context. The 26B pool allowed 23,000 tokens; the 31B k8s pod allows 15,000. If 8318 uses the same 15K cap, the EX agent's prompt budget (system template + retrieved contexts + history + tools) shrank by a third (inferred).
  • Reasoning. AGENT_LLM_REASONING_EFFORT=none keeps Gemma-4 from emitting a thinking block, which saves latency (:2477-2478).

Risks and open questions

  • Single point of failure: no LB, no health check, no retry pool. Ask SRE: is there a standby on another port?
  • Unknown flags: ask SRE for the launch command on 172.23.0.17:8318 (max-model-len, spec-decode, gpu-mem-util, vLLM version).
  • Host concentration: 172.23.0.17 also serves the shared-31B upstream :8319, COA :8310/8314/8321, zarebin :8311/8312, hakim-unsup :5113, hakim-search :8120, Qwen3.6 :8123 and gemma-embedding :4001/4002.
  • No metrics: add 8318 to prod/chatbot-inference-exporter/vllm-gemma4.yaml so tokens, TTFT and queue length are visible.
  • Hard-coded IP in app config: moving the server means editing EX values; an Envoy front would hide that.
